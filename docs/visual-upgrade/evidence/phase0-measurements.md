## 1. 这份文件是什么、为什么存在

`docs/visual-upgrade/LEDGER.md` 的几条承重行（`P0a-HARNESS-01` / `P0a-THRESH-01` / `P0a-GUARD-01` / `P0a-CLOCK-01` 与缺陷清单）

文件可以被改写、可以随机器丢失，而台账那一行会继续宣称一个没人能再验的数。
本文件把这些表**转录进 git**：引用者此后指本文件的**章节锚**（`§3.1` 等），落点即本文件所在的提交。

三条必须先说清的事实：

1. **数本身是对的，问题在出处。** 灵敏度阶梯被两条独立路线各量过一次并**逐点一致**（§5），
   报告作者与另一名并发代理各量各的 pixelmatch，报出的数一字不差。所以这是**出处耐久性**问题，不是正确性问题。
2. **没有一行已入库代码能重生成下面大部分数。** 逐条判定见 §2。
   算"最大单通道色差"与离线 pixelmatch 计数的脚本 `frontend/probe-analysis.cjs` 与 `frontend/probe-harness/`
   **用完即删、从未入库**（本会话实测两者在工作树与全部 git 历史中均不存在：
   `git log --all --oneline -- frontend/probe-analysis.cjs frontend/probe-harness` 无输出）。
   交付的探针把免检额 `console.log` 出来、**根本不读 diff 计数**。
   补这一条的是**计划 Task 4c Step 1g**（"让每一个被引用的数字都能一条命令重生成"）。本文件不承诺它何时落地。
3. **转录 ≠ 背书。** 报告里任何一处含糊、自相矛盾、或同一数字挂在两个不同配置上的，本文件**照实记在 §10**，
   不抹平、不择一个好看的写法。

### 4.3 逐像素闸（threshold）要求的最小单通道色差

这是**另一道闸**，与免检额不得混为一谈（spec §6 第 12 条；台账 `P0a-THRESH-01`）。
来源：`task-4b-report.md` 第 1 轮 §3-B 第 2 条的推导：pixelmatch 判据 `|colorDelta| > 35215·threshold²`，纯灰度差时 `colorDelta = 0.5053·Δ²`。

| threshold | 报告给的报警线（Δ/255） | 本会话按公式重算 |
| --- | --- | --- |
| 0.2 | Δ > 52.8 | √(35215/0.5053) = 264.0 ⇒ 264.0 × 0.2 = **52.8** ✓ |
| 0.1 | Δ > 26.5 | 264.0 × 0.1 = **26.4**（报告写 26.5，四舍五入差 0.1） |
| 0.05 | Δ > 13.2 | 264.0 × 0.05 = **13.2** ✓ |
| 0.02 | Δ > 5.3 | 264.0 × 0.02 = **5.28** ✓ |
| 0.01 | Δ > 2.6 | 264.0 × 0.01 = **2.64** ✓ |

台账 `P0a-THRESH-01` 写的 "`264.0×0.2`" 就是这个线性式，与报告的二次式同源、结果一致。
**推论（报告原话照抄）**：shadow 最大 Δ=20、radius 最大 Δ=19 ⇒ 与报警线"差一个数量级"，
所以"差异薄铺型改动被逐像素吸收"是定量形态；旧配置下**只调低 `maxDiffPixelRatio` 同样抓不到这个亮度注入**。

## 9. 日期漂移：字节差 vs pixelmatch 计数，与漂移带几何

来源：`task-4b-report.md` §R2.5（主证）、§R2.3（在 `{0.02, 0}` 整表跑里的那组计数）、§R2.4、`visual-helpers.ts@5675989` 注释。

**先钉住"两个数不是矛盾"**：同一对图（已提交基线 vs 用改动前代码今天截的图）有两个不同的"差多少"——

| 口径 | 数 | 它是什么 | 依赖配置吗 |
| --- | --- | --- | --- |
| **逐字节差** | **618** | 两图 PNG 解码后不相等的像素个数（无比较器参与） | **不依赖** threshold / ratio |
| **pixelmatch 计数** | **321** | 上面那些像素里，被 pixelmatch 判为"不同"的个数 | 依赖 `threshold`（t=0 下仍会跳过它判为抗锯齿的像素） |

⇒ **618 与 321 是同一件事的两层，不是互相矛盾**：差值 297 个是被抗锯齿分类器放行的。
这也是"降到 0 ≠ 逐字节比"的同一机制（§3.1 要点 3）。
**诚实标注**：报告把 "618 个逐字节差 / 321 个计数" 写在同一个括号里，**没有指名 618 属于四张里的哪一张**；
321 在 §R2.3/§R2.5 明确是 `student-dashboard` **明** 的计数，故本文件按该配对转录（§10.4）。

**漂移集合与计数（配置 `{threshold 0.02, ratio 0}` 的整表 anchors 跑，17 绿 / 5 张像素红）**：

| 锚点 · 主题 | pixelmatch 计数 | 性质 |
| --- | --- | --- |
| `student-dashboard` 明 | **321** | 日期漂移（确定性） |
| `student-dashboard` 暗 | **295** | 日期漂移（确定性） |
| `admin-governance-analytics` 明 | **110** | 日期漂移（确定性） |
| `admin-governance-analytics` 暗 | **111** | 日期漂移（确定性） |
| `student-courses-modal` 暗 | **13** | **真抖动**（不是漂移；见 §6 噪声地板的 1 px / 46 px 两次读数） |

**在交付配置 `{0, 0.0005}` 下这些漂移都被免检额吸收**：618 字节差 / 321 计数 **< 648**；
在旧配置 `{0.2, 0.002}` 下同样被吸收（2592 更宽）。⇒ **这正是 `ratio` 收不到 0 的唯一原因**（321 px 会直接点红）。

**漂移带几何（这是因果证明的另一半，不靠 md5）**：
差异全部落在图表的**时间轴标签行**——`student-dashboard` **y 537..544**、`admin-governance-analytics` **y 696..703**；
标签整组往后挪一天：

```
基线（10-18 截）：  10-05   10-06   10-07   10-08 …      2026-09-25  2026-10-01  2026-10-07
今日（10-19 截）：  10-06   10-07   10-08   10-09 …      2026-09-26  2026-10-02  2026-10-08
```

**根因**：`freezeClock` 只 fake 浏览器时钟，**图轴日期是后端按真实日期算出来的**。
代码侧落点（台账 `P0a-CLOCK-01` 已记）：`frontend/src/composables/useAnalytics.ts:535` 把后端返回的 `d.date`
直接铺进 x 轴。⇒ 这 4 张基线**只在截它的那一天有效，每天零点集体漂一次**。
**这条是"确定性而非抖动"的真正证明**：后端代码 + 漂移带的几何位置 + 标签整组平移一天。
跨次产物 md5 一致只是**佐证确定性**，不证明因果。

**确定性的佐证（md5，两种不同用途，别再混）**：

| md5 断言 | 配置/对象 | 它证明什么 | 今天能否重算 |
