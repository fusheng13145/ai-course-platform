## 二、逐项详述

### R-01 资源写操作全链路 500（P0）

**根因分析**
`Resource` 是 Lombok `@Data` 实体，字段 `private Boolean visibleToAll;` 由 Lombok 生成 `getVisibleToAll()`；而类内又**手写**了 `public Boolean isVisibleToAll()`。JavaBeans 规范中 `is` 前缀仅适用于基本类型 `boolean`，包装类型 `Boolean` 出现 `getXxx` 与 `isXxx` 两个 getter 即构成**重载歧义**，MyBatis 在解析实体属性时直接抛异常：

```
org.apache.ibatis.reflection.ReflectionException: Illegal overloaded getter method with
ambiguous type for property 'visibleToAll' in class 'com.aicourse.entity.Resource'
```

由于该异常发生在 MyBatis 反射建元数据阶段，**任何对 `resources` 的写操作都会失败**：上传资源、可见性切换、删除资源。这也解释了「读正常、写全 500」的现象。

**修复方案**：删除手写 getter，统一走 Lombok。

**修改关键点**
- `entity/Resource.java`：删除 `isVisibleToAll()`，并留注释说明「禁止为包装类型字段手写 `isXxx()`」。
- `service/impl/ResourceServiceImpl.java:49`：`resource.isVisibleToAll()` → `resource.getVisibleToAll()`。
- `test/.../ResourceServiceTest.java:200`：同步改为 `getVisibleToAll()`。

**验证方式与结果**
- 实机：`POST /api/resources/upload`（MP4/PDF）→ **200 并落库**；`PATCH /resources/{id}/visibility` → **200 且 `visible_to_all=0`**（用例 D3/D5/D10）。
- 对照组 `/api/common/upload` 全程正常，证明故障范围被准确界定。
- 单测 `ResourceServiceTest` 14/14 通过。

**回归影响**：🟢 极低。仅移除一个冗余方法；JSON 序列化字段名（`visibleToAll`）不变，前端无感知。

### R-02 进行中的考试被强制收卷（P0）

**根因分析**
`ExamTimeoutScheduler.autoSubmitExpiredExams()` 的类注释声明「超过时限（开始时间+时长 / 试卷结束时间，取较早者）才收卷」，但**实现中没有任何时间比较**：查询出全部 `STARTED` 会话后逐场调用 `timeoutSubmit`。调度周期为 30 秒 ⇒ **每场进行中的考试都会在最长 30 秒内被收卷**，考试时长形同虚设。实测：45 分钟时长的试卷，开考 40 秒后状态即变为 `AUTO_SUBMITTED`。

**修复方案**：补上时限判定与到期边界计算。

**修改关键点**（`scheduler/ExamTimeoutScheduler.java`）
- 注入 `ExamPaperService`；
- 新增 `resolveDeadline(session)`：`timeLimit`（无则 `duration`）+ `startTime` 得到时长边界，再与试卷 `endTime` 取**较早者**；
- 新增 `isExpired(session, now)`：未到期 `continue`（**关键修复点**）；
- **无任何时限依据时保守返回 false（不收卷）**，交人工处理，避免误收卷；
- 汇总日志改为「扫描 N 场，到期收卷 X 场，自动阅卷 Y 场，失败 Z 场」。

**验证方式与结果**
- 实机（J13）：45 分钟试卷开考后 **40 秒仍为 `STARTED`**（修复前为 `AUTO_SUBMITTED`）。
- 单测重写 `ExamTimeoutSchedulerTest`：原用例 `autoSubmitExpiredExams_submitsEachStartedSession` **恰好固化了缺陷行为**，已按正确语义重写，并新增「未到期不得收卷」（回归护栏）、「结束时间早于时长上限时按结束时间判定」、「无时限依据不收卷」等 6 例。

**回归影响**：🟠 中——**行为语义发生变化**：此前「所有 STARTED 会在 30s 内被收卷」，此后只有真正逾期的会话被收卷。这是修复目标本身。需注意：若某试卷既无 `time_limit`/`duration` 也无 `end_time`，将**永不自动收卷**，需由管理端 `force-submit` 兜底（已在报告中标注为策略点）。

### R-04 自动判分恒判错（P0）

**根因分析**
`questions.correct_answers` 为 **JSON 列**，单值写入 `"B"` 后按 String 读回得到的是**含双引号的文本** `"B"`；判分逻辑用
`studentAnswer.equalsIgnoreCase(correctAnswer)` 与作答 `B` 比较，**必然不相等** ⇒ 全部判错。实测：3 题全对，`total_score=0.00`（卷面 25.00）。

**修复方案**：判分前对两侧答案做「表示形态归一化」。

**修改关键点**（`service/impl/exam/ExamSessionGradingService.java`）
- 新增 `normalizeAnswer(String)`：JSON 字符串（`"X"`）→ 去引号标量 `X`；JSON 数组/对象 → 原样保留（多选题语义）；其余原样返回；
- 单值题（SINGLE_CHOICE / TRUE_FALSE）改用它比较，且**学生答案同样归一化**（兼容客户端提交带引号形式）；
- `parseArrayToStringSet()` 的失败回退由「整串作为一个元素」改为**按 `,，;；` 分隔符拆分**，与 DDL 注释「多答案按规则分隔/JSON 存储」一致（多选题部分匹配不再必然失配）。

**验证方式与结果**
- 实机（J7）：全对作答 → `status=GRADED`、`total_score=25.00`、`percentage=100.00`（修复前 0.00）。
- 单测 `ExamSessionGradingServiceTest` 10/10 通过。

**回归影响**：🟠 中——判分结果由「恒 0」变为「正确计分」，**历史考试会话的已存分数不会自动重算**（见「六、后续建议」）。多选题答案若此前以 `"A,B"` 形式提交，现在会按集合正确匹配，属修复而非破坏。

### R-05 选课/开考三类越权（P1）

**根因分析**
`CourseEnrollmentServiceImpl` 存在**两条并行入径且行为不一致**：
- `enroll()`：按课程 `enrollment_type` 推导审批态（APPROVAL → PENDING），但**无容量、无课程状态校验**；
- `enrollStudent()`（`POST /student/courses/{id}/enroll` 实际调用）：**恒置 `APPROVED`**，完全忽略 `enrollment_type`，且无任何容量校验。

同时对 `courses.approval_status` 与 `max_students` 无任何约束；`startExam()` 亦不校验学生与课程的选课关系。实测造成三条越权：
1. `APPROVAL` 课程被直接放行为 `APPROVED`；
2. `max_students=2` 时第 3 名学生仍成功入库（选课数=3）；
3. **未审批(PENDING)课程可被选课**；未选课学生可直接开考。

**修复方案**：两条入径收敛到同一组前置校验。

**修改关键点**
- `service/impl/CourseEnrollmentServiceImpl.java`：新增
  - `requireEnrollableCourse(courseId)`：课程必须存在；`approval_status ∈ {PENDING, REJECTED}` → 403「课程尚未通过审核，无法加入」；`status=INACTIVE` → 403「课程已结束」；
  - `assertCapacity(courseId, course)`：`max_students > 0` 时统计**有效选课记录数**（含 PENDING，因其占用名额），超限 → 400「课程选课人数已满（上限 N 人）」；
  - `initialApprovalStatus(course)`：`APPROVAL`/`RESTRICTED` → `PENDING`，否则 `APPROVED`（`enroll()` 与 `enrollStudent()` **共用**）；
  - `enrollStudent()` 不再硬编码 `APPROVED`，并补 `progress=0`。
  - 对 `approvalStatus/status` 为 **null 的历史数据保持放行**，避免存量数据与旧单测被误拒。
- `security/ExamSessionAccessControl.java`：新增 `assertExamStartable(examPaperId, auth)`——学生必须是该试卷所属课程的**有效选课学生**（`is_active=1`），否则 403「尚未加入该课程，无法参加考试」；教师/管理员不拦截（收卷/阅卷走 `force-submit`/`auto-grade`，保持原行为）。
- `controller/ExamSessionController.java`：`start` 入口调用该校验。

**验证方式与结果**
- 实机：C1 → **403 课程尚未通过审核**；G1 → 200 且落库 `PENDING`；G2 → `PENDING`；G4 → 200（第 2 人）；G5 → **400 课程选课人数已满（上限 2 人），选课数维持 2**；J1 → **403 尚未加入该课程**。
- 单测：`CourseEnrollmentServiceImplTest` 由 11 例扩到 13 例（新增「未审核课程拒绝」「满员拒绝」，并把原「课程不存在默认 OPEN」用例改为 **fail-fast 拒绝**），全部通过；`ExamSessionAccessControlTest` 新增 4 例开考校验，9 例全绿。

**回归影响**：🟠 中——**行为收紧**，属预期：
- 「课程不存在时按 OPEN 放行」的宽容行为被移除（原测试即为该行为的固化）；
- 审批型课程现在真的需要教师审批，前端若依赖「加入即可用」的即时态，需要展示「待审批」状态（前端已有该状态位）；
- 依赖「超员仍可入库」的压测/演示脚本需调整。

### R-06 试卷发布/组卷水平越权（P1）

**根因分析**
`ExamPaperController.publish` / `autoCompose` 仅做**角色**校验（`hasAnyRole(TEACHER,ADMIN)`），未做**归属**校验；`publishExamPaper()` 内部也只判断「存在 + 是否已发布」。实测 teacher2 可发布 teacher(张教授) 课程下的试卷，返回 200、`status` 置为 `PUBLISHED`，并**触发向该课程学生推送考试通知**。

**修复方案**：与既有 `ExamSessionAccessControl` / `SubmissionAccessControl` 同构，新增试卷对象级授权组件。

**修改关键点**

**验证方式与结果**

### R-03 空作答阅卷周期性 ERROR（P1）

**根因分析**：超时收卷后无条件调用 `autoGrade`，而 `autoGrade` 在 `answers` 为空时抛 `BusinessException("未找到学生作答记录")`，被调度器以 ERROR 记录 ⇒ 每 30 秒刷屏（实测 sessionId=1/3/5/7）。

**修改关键点**：`ExamTimeoutScheduler` 新增 `hasAnswers(session)`，无有效作答时**跳过自动阅卷并记 WARN**（收卷本身仍执行，语义不变）。

**验证与影响**：运行时日志中该类 ERROR 计数由 4 → **0**；单测新增「无作答收卷但不阅卷」用例。🟢 低。

### R-07 认证/授权与错误语义（P2）

**根因分析（分三层）**

1. **已登录越权返回 401（关键）**：`SecurityConfig` 只配置了 `authenticationEntryPoint`，未配置 `accessDeniedHandler` ⇒ 使用默认 `AccessDeniedHandlerImpl`，它通过 **`response.sendError(403)`** 让容器走 **ERROR 转发**；而 `JwtRequestFilter`（`OncePerRequestFilter`）**默认跳过 ERROR 转发**（`shouldNotFilterErrorDispatch()==true`）⇒ 在 ERROR 转发的二次安全校验中上下文为空（匿名）⇒ `ExceptionTranslationFilter` 判定「未登录」⇒ 调用 EntryPoint 输出 **401**，把原本的 403 覆盖。
   *旁证*：响应头出现 `Set-Cookie: JSESSIONID`（`sendStartAuthentication` 保存请求缓存所致）；而 `/student/**` 的拒绝发生在**方法级**安全（`AccessDeniedException` 被 `@RestControllerAdvice` 直接处理），不经 `sendError`，故稳定返回 403 —— 同一系统两套口径。
   **用户可见后果**：前端 `api/request.ts` 把 401 映射为「登录已过期，请重新登录」，并在刷新失败后调用 `/auth/logout` + `router.push('/login')` ⇒ **学生只是访问了无权页面，却被登出并踢回登录页**。
2. **业务越权返回 400**：`CourseServiceImpl.updateCourse` / `TeacherController.assertCourseOwner` 抛的是**默认码** `BusinessException(String)`，被映射为 400。
3. **约束冲突/上传超限返回 500**：`GlobalExceptionHandler` 无 `DuplicateKeyException` / `MaxUploadSizeExceededException` 分支，落入兜底 500。

**修复方案**
- 新增 `security/RestAccessDeniedHandler`：直接写出 `403 {"code":403,"message":"权限不足，禁止访问"}`（**不经 `sendError`，从根上规避 ERROR 转发的匿名化**），并在 `SecurityConfig.exceptionHandling` 显式注册；
- `JwtAuthenticationEntryPoint` 改为**上下文感知**：已认证（非匿名）→ 403；未认证/匿名/令牌失效 → 401（纵深兜底，并输出 user/roles 便于排障）；
- `GlobalExceptionHandler` 新增：`DuplicateKeyException` → **409**「数据已存在（唯一约束冲突）…」、`DataIntegrityViolationException` → 400、`MaxUploadSizeExceededException` → **413**；兜底分支沿因果链识别容器层 `SizeLimitExceededException` → 413；
- `ApiCode` 新增 `CONFLICT=409` / `PAYLOAD_TOO_LARGE=413`；
- 越权业务异常统一改为 `ApiCode.FORBIDDEN`（`CourseServiceImpl.updateCourse`、`TeacherController.assertCourseOwner`）。

**验证方式与结果**

### R-12 课程审批后未失效缓存（P1，修复过程中新暴露）

**发现路径**：R-05 为选课加了「课程必须已审核」校验后，端到端用例 G1 突然失败并提示「课程尚未通过审核」——而此时 C4 已审批成功。据此定位到缓存问题。

**根因分析**：`CourseServiceImpl.getById` 标注 `@Cacheable(cacheNames="courses", key="#id")`（Redis 缓存），而 `approveCourse` / `rejectCourse` / `toggleCourseStatus` / `deleteCourseById` **均未标注 `@CacheEvict`**。审批写库后，`getById` 在 TTL 内仍返回**旧的 PENDING 快照** ⇒ 跨请求状态不一致（表现为「审批已通过，但加入课程/统计/校验仍认为未审核」）。

**修复**：四处写操作补齐 `@Caching(evict = { key=#id, key='all' })`（单条 + 列表一起失效），与既有的 `updateCourse`/`save` 写法保持一致。

**验证**：修复后 G1 → 200 且落库 `PENDING`；DB 终态 `courses.approval_status=APPROVED`；端到端全绿。

**回归影响**：🟢 低（写后失效是缓存标准用法，仅增加一次缓存删除）。**建议**：审查其余 `@Cacheable` 实体是否也存在「写路径缺 evict」的同类问题（见后续建议）。
