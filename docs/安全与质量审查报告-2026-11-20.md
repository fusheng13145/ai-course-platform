## 01 安全边界表

**风险是什么**：边界不清会导致“某条路径以为框架会拦、实际没人拦”。本项目有 71 个 Controller / 519 个方法级 HTTP 映射，单靠 URL 规则一定会漏。

**当前在哪里处理（按边界分层）**

| 边界 | 风险 | 处理位置 | 处理规则 | 验证状态 |
| --- | --- | --- | --- | --- |

| 登录状态 | 伪造/过期/已登出令牌继续用 | `JwtRequestFilter` → `JwtUtils` → `UserSessionService#isSessionActive` | HS256 验签 + iss/aud + 会话活跃 + 过期；每次请求查 Redis 缓存/回源 DB | 已验证（`JwtRequestFilterTest` 15 例） |
| 系统权限 | 学生调管理员接口 | `SecurityConfig` URL 规则 + 230 处 `@PreAuthorize` + `AdminScopeGuard` | `/admin/**` 仅 ADMIN；写操作仅 TEACHER/ADMIN；admin 再按学院收口 | 已验证（学生调 `/admin/users` 实机 403） |
| 密码规则 | 弱口令、明文存储 | `PasswordPolicy` + `BCryptPasswordEncoder` | 8–32 位、四类字符；BCrypt 存储 | 已验证（DB 非 BCrypt 行数 = 0） |

## 02 接口输入

**风险是什么**：关键参数（身份、权限、金额/容量、数据归属、DB 写入）若只靠前端，改包即可越权。

**关键参数与校验位置（抽样 12 类，覆盖全部写入口模式）**

| 接口 | 来自前端的参数 | 影响面 | 校验位置 / 规则 | 校验失败返回 | 证据 |
| --- | --- | --- | --- | --- | --- |
| `POST /auth/login` | `username`、`password`、`rememberMe` | 身份 | `UserLoginDTO` `@NotBlank`；服务层查库 + BCrypt 比对 + `(IP,账户)` 节流 | 400 `用户名或密码错误`；429 `登录尝试过于频繁` | 实机：4 次失败后 429 |

| `POST /ai/qa/ask` | `question/courseId/sessionId` | LLM 成本、课程数据 | `QaAskDTO` `@Size(max=4000)`；课程可读性 ACL；会话归属 + 课程一致性 | 400/403 | 静态 + `AiQuotaService` |

**校验失败返回的两套口径（真实风险）**：全局异常走 `ResponseEntity`（HTTP 400/403/404/429）；但部分 Controller 内 `ApiResponse.error(400, ...)` 直接 return，**HTTP 仍是 200**。实机上传拒绝即 `HTTP=200`、body `message=不支持的文件类型`。前端按 body `code` 判断能工作，但网关/WAF/监控无法按状态码识别攻击，且与“HTTP 语义”不一致。

**结论：⚠️ 有风险**——关键参数都有服务端校验，但错误状态码不统一，且确认密码这类业务规则存在“前端才校验”的缺口。

## 03 登录与权限

**风险是什么**：URL 级规则漏一条，或方法级注解写错一个表达式，就是越权。

**权限设计表（按域抽样，覆盖全部 519 条的三层模型）**

| 接口组 | 是否需要登录 | 允许角色 | 只能操作自己的数据 | 管理员可否访问 | 判断位置 | 无权限返回 | 测试证明 |
| --- | --- | --- | --- | --- | --- | --- | --- |

## 04 会话与令牌

**风险是什么**：令牌可被 XSS 读取、退出后仍有效、改密后旧会话继续用、Cookie 被跨站携带。

| 项 | 现状 | 位置 | 验证 |
| --- | --- | --- | --- |
| 生成 | jjwt 0.12.6，HS256；`iss=aicourse-platform`、`aud=aicourse-web`、`jti`、`sub=userId` | `JwtUtils` | 验签失败/过期用例在 `JwtRequestFilterTest` |
| 密钥 | `JWT_SECRET` 无默认值，缺失即启动失败；本机 64 字符（OK） | `application.yaml` + `audit-stats.py` | 已验证 |
| 存放 | Access Token 放 `HttpOnly` Cookie `ai_course_token`；Refresh Token 放 `HttpOnly` Cookie，Path 限定 `/api/auth/refresh`；**两者都从响应体移除** | `AuthController#issueAuthCookiesAndStripBody` + `CookieUtils` | 实机登录 body 无 `token` 字段 |
| Cookie 属性 | `HttpOnly=true`；`SameSite=Lax`；`Secure` 由 `COOKIE_SECURE` 控制，默认 true | `CookieUtils` + `application.yaml:234` | 实机响应头（本地 Secure=false，生产 true） |
| 有效期 | 普通 1 天 / 记住我 7 天；刷新令牌同会话 `expires_at` | `JwtUtils` + `AuthSessionComponent#buildUserSession` | 静态 |
| 退出登录 | 将该用户**所有**活跃会话置 `is_active=0`，逐条 evict Redis 缓存 | `AuthSessionComponent#logout` | 代码；`AuthCookieTest` |
| 改密/重置 | 成功后吊销该用户全部会话，旧令牌立即失效 | `AuthPasswordComponent` | 代码；`JwtRequestFilterTest` 会话无效用例 |
| 刷新 | 每次轮换 refreshToken（旧值作废）+ evict 旧 access 缓存；校验 `is_active` 且 `expires_at > now` | `AuthSessionComponent#refreshToken` | 静态 |
| 每请求校验 | 验签后必须 `isSessionActive(token)`（Redis 优先、DB 回源）；角色从 DB 取，不信任 JWT 内角色 | `JwtRequestFilter` | 15 例测试 |
| 框架/自研 | 用 Spring Security + jjwt，未自研加密；CSRF 是自研 Filter（见 09） | — | — |

**发现的风险**
1. **Access Token 在库内明文**：`user_sessions.session_token` 直接存 JWT。实机读数：`session_token LIKE 'eyJ%'` = **2051 行**；refresh_token 为 64 位 SHA-256 = 2051 行。DB 泄露/备份泄露即可在令牌过期前重放（1–7 天）。建议存 `sha256(token)`，校验时哈希比对；或至少加密列。
2. **登出 CSRF**：`/api/auth/logout` 在 CSRF 豁免名单，第三方页面可强制受害者登出（低危，但属于“登出即失效”的可用性攻击）。
3. **Redis 故障降级**：登录节流失效（fail-open），限流退化为本机内存（多实例不一致）。可用性优先的取舍，需在部署文档写明。
4. **会话过期与刷新令牌不一致（非安全）**：刷新总是签发 7 天 access token，但 `expires_at` 不变；普通会话 1 天后刷新也失败。安全上更严，功能上是 bug。

**结论：⚠️ 有风险**——吊销链路完整，唯一实质性缺口是 access token 明文落库。

**风险是什么**：弱口令、明文、入口旁路、爆破。

**未实现/缺口**
1. **无常见弱口令字典拦截**：`Admin@123456`、`Password123!` 均能通过（只校验字符类别）。这是当前最高频的真实风险。
2. **无用户名/邮箱相似度校验**、无密码历史、无泄露库比对。
3. **批量导入绕过策略**（JSON 与 Excel 两条路径），可一次导入 100 个 `123` 口令账号；仅 ADMIN 可触发，但属于“配置名义落地弱口令”。

6. **两套密码长度口径冲突**：DTO 6–30 / 策略 8–32；31–32 位强密码会被 DTO 拒绝。

**结论：⚠️ 有风险（高）**——BCrypt 与节流合格，但“弱口令字典 + 批量导入旁路”必须在上线前收口。

## 07 注入风险

**风险是什么**：SQL/命令/模板拼接。

**SQL**
- 数据访问统一 MyBatis-Plus：`LambdaQueryWrapper` / `@Select` 全部 `#{}` 参数绑定；mapper XML 与 Java 源码中 **未发现 `${}` 拼接**（`Select-String` 仅命中 `@Value` 与 logback）。
- 唯一字符串拼接：`LoginLogServiceImpl:406` `.last("LIMIT " + limit)`，`limit` 为 `int` 且夹取 1–100，**不可注入**。
- 动态排序/字段名：未发现从请求直接拼 `orderBy`。

**命令**
- `SysBackupComponent` 使用 `ProcessBuilder` 数组、`--defaults-extra-file` 传凭据、不经 shell；`fileName` 有五道路径校验（分隔符、`..`、绝对路径、normalize、目录前缀）。
- **但 `targetDb` 直接拼进 SQL 字符串**：``execMysql(tempConfig, "CREATE DATABASE IF NOT EXISTS `" + resolvedDb + "` ...")``。`targetDb` 只校验“等于当前库”或“以 `aicourse_restore_`/`restore_` 开头”，**未限制字符集**。构造 `aicourse_restore_x\`; DROP DATABASE ai_course_platform; --` 可闭合反引号执行任意 SQL。入口：`POST /admin/system/backup/{fileName}/restore`，ADMIN + 本校管理员。虽为高权限功能，仍属注入，且可越过“只允许隔离库”的护栏。

**HTML/模板**
- 后端只返回 JSON，无服务端模板渲染；邮件正文中的验证码为 6 位数字，无用户可控 HTML。
- 前端 XSS：`sanitize.ts` 使用 DOMPurify 3.4.17；`v-html` 仅用于清洗后的课程/公告富文本；`xssSurface.test.ts` 守卫。
- **但存储型 XSS 仍有一条绕过路径**：分片上传允许 `.svg`，本地存储模式由 Spring 静态处理器按扩展名回 `image/svg+xml` 且内联展示（见 08）。

**日志注入**：上传原始文件名进日志，未过滤 CRLF，可伪造日志行；低危。

**结论：⚠️ 有风险（高）**——常规 SQL 注入防线成立，但备份恢复的 `targetDb` 是真实注入点。

## 08 文件上传

**风险是什么**：脚本执行、存储型 XSS、路径穿越、磁盘打满、越权下载。

| 项 | 现状 | 位置 | 验证 |
| --- | --- | --- | --- |
| 类型判定 | `/common/upload`：扩展名白名单 + **魔数**（png/jpg/gif/pdf/zip/docx 等）；分片上传：扩展名白名单（含 svg/json/xml），**分片无魔数、合并后置 `application/octet-stream` 元数据** | `UploadMagic` / `CommonController` / `FileUploadSessionServiceImpl` | 实机：html 拒绝、假 PNG 拒绝、真 PNG 通过 |

| 存储位置 | 本地 `data/aicourse-platform/storage/YYYY/MM/`（webroot 外）；MinIO `aicourse-uploads` | `StorageLayout` / `LocalFileStorageServiceImpl` | 实机 URL `/uploads/...` |
| 重命名 | UUID 文件名；原始名只存展示/日志 | `CommonController` | 实机 URL 为 UUID |
| 脚本执行 | 不在 webroot；静态服务只读；无 `jsp/php` 执行环境 | `UploadResourceConfig` | 静态 |

**确认的风险**
1. **SVG 存储型 XSS（高）**：任意已登录学生可 `POST /upload-sessions`（`fileName=evil.svg`）→ 上传 1 片 → merge → 得到 `/uploads/YYYY/MM/uuid_evil.svg`。本地模式由 `ResourceHttpRequestHandler` 按 `.svg` 返回 `image/svg+xml` 内联，SVG 内脚本在**同源**执行；HttpOnly 只保护 token 不被读，但同源 JS 可带 Cookie 调 API、读 `XSRF-TOKEN`，等价账户接管。MinIO 模式被 `safeMediaType` 降为 octet-stream，风险仅在 `MINIO_ENABLED=false`（默认本地/评测）成立。

**结论：⚠️ 有风险（高）**——`/common/upload` 这条主路径是合格的（白名单+魔数+UUID+登录+ACL），分片上传是缺口。

## 09 跨站与安全响应头

**风险是什么**：Cookie 登录下的 CSRF；CORS 放开任意来源；缺 CSP/HSTS。

| 项 | 现状 | 位置 | 验证 |
| --- | --- | --- | --- |
| CSRF 机制 | 自研双提交 Cookie：32 字节 `SecureRandom` token，`XSRF-TOKEN` 非 HttpOnly + `X-XSRF-TOKEN` 头，常量时间比较；Spring Security CSRF 明确关闭避免双份 | `DoubleSubmitCsrfFilter` / `SecurityConfig:283` | `DoubleSubmitCsrfFilterTest` 6 例 |
| 豁免 | `/api/auth/login|register|refresh|logout|verify-code`、`/api/common/verify-code`、`/api/monitor/frontend-error` | `DoubleSubmitCsrfFilter#EXEMPT_PREFIXES` | 代码 |
| SameSite | `Lax` | `CookieUtils` | 实机响应头 |
| CSP | `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'; object-src 'none'` | `SecurityConfig:292-295` | 静态 |
| HSTS | 1 年 + includeSubDomains（仅 HTTPS 响应） | `SecurityConfig:288-290` | 静态 |
| 其他头 | `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer` | 同上 | 静态 |
| CORS | 白名单 + `allowCredentials=true`；prod 空列表 + `dev-fallback=false`（fail-closed），由 `CORS_ALLOWED_ORIGINS` 注入 | `SecurityConfig#corsConfigurationSource` + `application-prod.yml:109` | `check-https-ws-config.py` 实测 FAIL：CORS 为空 |
| 本地开关 | `start-all.py:467` 置 `CSRF_ENABLED=false` | `scripts/start-all.py` | 实机：无 CSRF 头仍进入业务（400 原密码错误），证明本机 CSRF 关闭 |

**确认的问题**
1. **CORS `allowedHeaders` 缺 `X-XSRF-TOKEN`**（`SecurityConfig:421-422`）。同源部署（Vite 代理/nginx 同域）不受影响；一旦按文档跨域部署（前端独立域名），所有写请求预检失败 → CSRF 头被浏览器拦截。**功能故障，不是漏洞**，但会让“跨域可用”承诺失效。
2. **生产 CORS 未配置**：`check-https-ws-config.py` 对 `deploy/env.production` 报 `[FAIL] CORS_ALLOWED_ORIGINS：为空`，且该文件根本不存在（只有 template）。
3. **本地启动器关闭 CSRF**：只应存在于 dev；但它是 `start.bat` 默认行为，若有人拿 8080 当“内网试用环境”直接暴露，CSRF 防护为 0。生产 compose 默认 `CSRF_ENABLED=true`，风险限于误用启动方式。
4. **登出豁免 CSRF**：见 04。

**结论：⚠️ 有风险**——CSRF 实现与响应头是合格甚至优秀的，问题在“环境开关与跨域头配置”。

## 10 SSRF

**风险是什么**：服务器替用户请求任意 URL，打内网/云元数据。

**结论先行：本项目没有“用户提供 URL、服务器去请求”的功能。**
- 全仓 `RestTemplate/WebClient/HttpClient/new URL/openConnection` 仅用于固定外部端点：DeepSeek/OpenAI/Qwen/Ollama、Python KG(8001)/RAG(8002)/FT(8003)、SMTP、MinIO。地址全部来自配置（`DEEPSEEK_BASE_URL`、`OLLAMA_BASE_URL`、`RAG_BASE_URL` 等），无请求参数进入 URL。
- 管理员只能切换 `provider` 名称（deepseek/openai/qwen/ollama），不能改 base URL；`SystemConfigController` 无“webhook URL/抓取 URL”入口。
- 用户可控的 `avatarUrl`、`fileUrls`、`notification.actionUrl` 只是字符串，由**浏览器**加载，不是服务端请求；不构成 SSRF（但外部图片可被用于客户端追踪，低危）。

**仍建议**：生产出网做 allowlist（只允许 `api.deepseek.com`、`*.ollama` 内网、SMTP、MinIO），禁止 169.254.169.254/元数据网段；`INTERNAL_API_KEY` 目前默认空，Python 服务在本机监听时任何本机进程可调用——这是“内网信任”问题，不是 SSRF。

**结论：✅ 通过**（功能不存在；出网白名单属加固建议，非缺陷）。

## 11 数据库操作

**风险是什么**：拿前端 ID 直接改删、缺归属校验、缺审计、硬删除导致不可恢复。

**规模**：Flyway 结构迁移 26 个；运行库 **62 张表**（`information_schema` 实测）；`@Transactional` 250 处。

**重要数据与操作（抽样 14 张，覆盖高风险面）**

| 表 | 读接口 | 写接口 | 删接口 | 身份/权限/归属 | 业务规则 | 软删/事务/审计 |
| --- | --- | --- | --- | --- | --- | --- |
| `users` | `/users/{id}`、`/admin/users` | 注册、`/admin/users`、导入 | `DELETE /admin/users/{id}` | 本人或 ADMIN + 学院收口 | 唯一用户名/邮箱、禁用态 | **无 `@TableLogic`，实为硬删**；`@Transactional`；操作日志 |
| `user_sessions` | `/auth/sessions` | 登录、刷新 | 登出/改密批量置无效 | 本人 | 过期、活跃态 | 软失效 + 事务 |
| `courses` | 列表/详情 | 教师 CRUD | 教师删除 | 开课教师/选课学生/ADMIN | 课程状态、容量 | 事务；操作日志 |
| `course_enrollments` | 我的选课/名单 | 选课、审批、退课 | 退课置 `CANCELLED` | 学生本人/本课教师 | 课程行 `FOR UPDATE` + 容量 + 唯一 | 事务；状态机 |
| `resources` | 列表/下载 | 教师上传/更新 | 教师删除 | `ResourceAccessSupport` | 可见性、课程归属 | 版本表 + 事务 |
| `submissions` | `/submissions/{id}`、列表 | 学生提交 | 教师/管理员 | `SubmissionAccessControl` | 尝试次数唯一键 `uk_submissions_task_student_attempt` | 事务；操作日志 |
| `exam_sessions` | 我的考试/监考 | 开考、交卷 | — | 学生本人/本课教师 | 试卷行 `FOR UPDATE`；**无 `(student,paper)` 唯一键** | 事务；监考事件 |
| `exam_questions` | 试卷 | 组卷 | 教师 | 本课教师 | 题目归属 | 事务 |
| `grade_items` | 成绩 | 评分/导入 | — | 本课教师 | 分数范围 | 事务 |
| `operation_logs` | `/admin/logs`（文件日志，不是此表） | AOP 自动写 | — | — | 仅写操作 | 独立保存；19,575 行 |
| `login_logs` | 管理端 | 登录时写 | — | — | 成功/失败 | **失败日志随登录事务回滚**（见 16） |
| `verification_codes` | — | 发送/校验 | 过期清理 | — | 5 分钟、一次性 | 明文 6 位码 |
| `system_configs` | `/admin/configs` | ADMIN | — | 本校管理员 | 键值 | 操作日志 |
| `file_upload_sessions` | 管理端 | 分片上传 | 完成/取消 | 上传者/ADMIN | 归属、分片序号 | 事务 |

**确认的问题**
1. **`users` 硬删除**：全局 `logic-delete-field: deleted` 配置存在（`application.yaml:198`），但**没有任何实体有 `deleted` 字段**；`removeById` 走物理 DELETE。用户删除后其提交/成绩/日志成为孤儿（部分表有 FK `ON DELETE CASCADE`，会连带删除证据）。需要明确“删号”策略：软删或先归档。
2. **失败登录审计丢失**：`AuthSessionComponent#login` 在 `@Transactional(rollbackFor=Exception.class)` 内 `saveLoginLog(...FAILURE...)` 后抛 `BusinessException` → 整事务回滚。实机证据：13:29:59–13:30:00 有 6 条 `operation_logs` FAILED，但 `login_logs` **没有对应失败行**（最新仅 13:29:58 学生成功）。
3. **考试会话缺数据库唯一兜底**：`exam_sessions` 仅有普通联合索引 `idx_exam_sessions_student_paper`，不是 UNIQUE；开考靠 `exam_papers` 行锁串行化，逻辑上安全，DB 层无最后防线。
4. **直接按前端 ID 改删**：管理员接口大量 `PUT/DELETE /admin/.../{id}` 属设计内；非管理员侧未发现“只凭 ID 无 ACL”的写删（提交/资源/课程均有对象级校验）。

**结论：⚠️ 有风险**——权限与事务覆盖好，硬删除与失败审计是两份真实缺口。

## 12 业务逻辑与并发

**风险是什么**：超卖、重复提交、重复扣额、关键步骤跳过。

**业务类型说明**：本项目**没有支付、退款、领券、提现**；核心写业务是选课容量、作业提交、考试开考/交卷、评分、AI 额度。

| 流程 | 后端重新校验 | 防重/并发 | 能否跳步 | 验证 |
| --- | --- | --- | --- | --- |
| 选课 | 课程状态、是否已选、容量 | 课程行 `SELECT ... FOR UPDATE` 串行化同课程；`COUNT ... FOR UPDATE`；`(student,course)` 业务唯一 | 审批流由教师端点控制 | 代码 + Mapper 注释；**未压测** |
| 退课 | 状态、原因、结课门禁 | 状态机 `CANCELLED` | 需先有有效选课 | 代码 |
| 作业提交 | 任务归属、尝试次数、内容长度 | DB 唯一键 `(task_id,student_id,attempt_number)`；并发冲突 → 409 | 不能改 `score/graderId`（DTO 白名单） | `SubmissionControllerSecurityTest` 7 例 |
| 作业评分 | 教师本课、分数范围 | 更新单行；无版本号 | — | 代码 |
| 考试开考 | 试卷状态、时间窗、学生资格 | 试卷行 `FOR UPDATE`（**同卷所有学生串行**）；无学生级唯一键 | 不能重复开考（逻辑判定） | 代码；**未并发验证** |
| 交卷 | 会话归属、状态、时限 | 状态机；重复交卷应拒绝 | — | 代码 |
| AI 问答 | 课程可读、会话归属、课程一致性 | 100 次/天 + 20 万 token/天，Redis Lua 原子 | 不能跨课程复用会话 | 代码 |
| 文件上传 | 扩展名、大小、会话归属 | 仅会话级分片序号；**无总量配额** | — | 实机 |

**确认的风险**
1. **开考锁粒度太大**：`ExamPaperMapper#selectByIdForUpdate` 锁试卷行，同一试卷的所有学生开考被串行化。100 人同时开考会排队；若某请求持锁慢（DB 慢查询），其他人超时。建议改为“学生级唯一键 + 插入冲突处理”，试卷行锁只用于组卷/发布。
2. **容量校验依赖行锁而非约束**：课程行锁正确，但 `course_enrollments` 是否有 `(course_id,student_id)` 唯一键未在迁移中确认（代码有重复校验）。双实例/绕过入口仍可能重复选课。
3. **无幂等键**：提交靠唯一键，重复请求返回 409 而非幂等返回同一结果；前端需处理。
4. **AI 配额 fail-open**：Redis 故障时额度可能失效（成本风险），需确认 `AiQuotaService` 降级策略。

**结论：⚠️ 有风险**——关键流程都有后端校验和至少一道并发防线，但没有并发压测证据，锁粒度存在可用性风险。

## 13 敏感数据保护

**风险是什么**：明文存储、过度收集、接口多返字段、备份泄露。

| 数据 | 存储形态 | 传输 | 接口暴露 | 评价 |
| --- | --- | --- | --- | --- |

| 学号/专业/年级 | 明文 | HTTPS | 本人/教师/管理员 | 低敏 |

**传输**：prod `require-https=true` + `COOKIE_SECURE=true` + HSTS；本地 `false`（明文联调）是预期配置，但**同一 `.env` 若被拿去部署就是明文令牌**。

**结论：⚠️ 有风险**——数据收集克制、密码/刷新令牌合格；access token 明文与备份未加密是两处需要决策的点。

## 14 过度防御检查

**风险是什么**：重复判断、永不成立的分支、为安全感堆封装，增加维护成本并掩盖真实缺口。

| 判断 | 性质 | 是否应保留 | 说明 |
| --- | --- | --- | --- |
| URL 角色规则 + `@PreAuthorize` + 对象 ACL | **三层不同作用域**，不是重复 | 保留 | URL 拦角色、注解拦方法、ACL 拦数据归属；缺一层都会漏 |
| DTO 校验 + 服务层 `PasswordPolicy` | 防御纵深，但**口径冲突** | 保留一层强规则，统一口径 | 6–30 vs 8–32 会让 31–32 位密码白填 |
| `AuthController#requireLogin`（`/auth/**` permitAll 下判 null） | 必要 | 保留 | 否则匿名改密会 NPE/500 |
| `CookieUtils` 默认 `secure=false` + yml 默认 true | 配置覆盖，不是死代码 | 保留 | 但注释“local profile”与实际不符（无 `application-local.yaml`） |
| `logic-delete-field: deleted` | **死配置** | 删除或实现 | 无实体有 `deleted` 字段，实际全硬删 |
| `users.failed_login_attempts` | **半死字段**：登录成功清零，失败不再递增 | 迁移时清理 | 账户级锁定已改为 Redis `(IP,账户)` 节流；`locked_until` 仍保留给管理员手工锁定 |
| `PUT /auth/password` “备用接口” | 重复 API 面 | 合并/下线 | 与 `/auth/change-password` 完全同一逻辑，多一个 CSRF/鉴权面 |
| `GET /common/feature-roadmap` | **写死假数据 + 公开** | 删除 | 仅返回 5 条硬编码功能状态，前端视图未使用（只有 api 封装与 passthrough 测试） |
| `GET /admin/ai/test`、`POST /admin/configs/test-email` | 运维诊断，非调试垃圾 | 保留但限流/审计 | 前者触发付费 LLM，后者可发信；ADMIN 专用 |
| `ALERTMANAGER_WEBHOOK_URL`（example 有、无消费者） | 死配置键 | 删除或接线 | `audit-stats.py` 明确“example 中无任何代码消费者的键数=1” |
| `CSRF` Spring 关闭 + 自研 Filter | **单一实现**，不是双份 | 保留 | 若同时开启会双校验冲突，注释已说明 |

**结论：⚠️ 有风险（低）**——没有出现“为了安全感新增重复判断”的迹象；需要清理的是死配置与重复 API 面，不是再加封装。

## 16 日志安全与埋点

### （A）日志安全

| 日志 | 记录内容 | 是否含敏感数据 | 位置 |
| --- | --- | --- | --- |
| 请求日志 | **没有全局 access log**；只有业务 `INFO` 与审计表 | 不含 body | `logback-spring.xml` |
| 业务日志 | 登录/注册/上传/异常等，带 `traceId` | 无密码/token；异常消息可能含 SQL/表名 | `AuthSessionComponent` 等 |
| 审计日志（DB） | 所有写接口的 method/target/params/用户/IP/UA/耗时/状态 | `password/oldPassword/newPassword/confirmPassword/code/authorization/accessToken/refreshToken/token/secret/apiKey/accessKey` 统一 `***` | `OperationLogAspect:81-125` |
| 错误日志 | `GlobalExceptionHandler` 的 WARN/ERROR | 返回体只给业务消息；堆栈只进服务端日志 | `GlobalExceptionHandler` |
| 登录日志 | `login_logs` 成功/失败/登出 + IP/UA/原因 | 无密码 | `AuthSessionComponent#saveLoginLog` |

**实际样本（2026-11-20，`logs/api.log`）**

正常请求：
```
2026-11-20 13:29:59.592  INFO [21df68fa88ff4124] --- [io-8080-exec-17] c.a.s.c.auth.AuthSessionComponent : 登录认证
```
错误/限流：
```
2026-11-20 13:29:59.668  WARN [0d04c2fed2de41ad] --- [nio-8080-exec-5] c.a.exception.GlobalExceptionHandler : 业务异常[code=429]：登录尝试过于频繁，请15分钟后再试
```
系统错误样本（依赖不可用）：
```
2026-11-20 13:37:40.629  WARN [] --- [scheduling-1] c.a.h.PythonServicesHealthIndicator : rag 健康检查失败: I/O error on GET request for "http://localhost:8002/api/v1/rag/health": Read timed out
```

**确认的问题**
1. **失败登录的业务日志被事务回滚**：见 11；`login_logs` 只剩成功/登出，失败爆破在库里无痕（仅 `operation_logs` 有 FAILED 行，且 params 为 NULL）。
2. **`OperationLogAspect` 序列化失败率高**：Controller 参数含 `HttpServletRequest/Response` 时 Jackson 抛异常，`params` 留空并打 WARN。实机 13:29:59 每笔登录都出现“序列化操作日志参数失败”，导致审计缺参数。应改为“只序列化 DTO/Map，跳过 Servlet 对象”。
3. **本地日志不落盘/不滚动**：`logback-spring.xml` 仅 prod 加 FILE appender；dev 是 `start-all.py` 的 stdout 重定向到 `logs/api.log`，无大小上限（现 8.2MB，持续增长）。生产有 50MB/天、30 天、2GB 上限。
4. **`error_msg` 存异常消息**：可能含 SQL 表名/字段名，管理端可见；可接受但应截断（已截 500）。
5. **日志注入**：上传原始文件名可含换行，写日志可伪造行；低危。

### （B）关键功能运行日志

| 功能 | 是否有日志 | 内容 | 评价 |
| --- | --- | --- | --- |
| 登录 | 是 | `登录认证`（INFO）+ 成功/失败入 `login_logs` + 审计表 | 成功链路完整；失败链路被回滚（需修） |
| 注册 | 是 | `注册认证` + 审计 | ✅ |
| 上传 | 是 | 成功/失败、路径、大小；不含文件内容 | ✅ |
| 下单/支付 | 不适用（无此业务） | — | — |
| 评分/成绩 | 是（AOP 写操作审计） | 方法、用户、参数（脱敏）、耗时、状态 | ✅ |
| AI 调用 | 是 | `ai_call_logs` + 失败降级日志 | ✅ |

**结论：⚠️ 有风险**——脱敏设计正确、没有打印密码；但“失败登录审计回滚”和“审计参数为空”让关键排障证据缺一半。

## 17 依赖安全

**风险是什么**：已知 CVE、过期版本、供应链。

**后端直接依赖（`backend/pom.xml`，Java 21 / Spring Boot 3.5.16）**

| 依赖 | 版本 | 用途 | 风险关注 |
| --- | --- | --- | --- |
