# 现有项目完成度与漏洞评估方案

## 一、文档性质与目的

本文档定义对「现有项目」完成度与质量的深度评估方法，用于消除「不了解现有代码、怕看不深」的担忧。全文独立成篇，作为后续接收申报书、论文、参考项目、现有项目文档与代码后的评估执行纲领。

## 二、评估前提

现有项目已具备多端骨架（`backend/` Java、`frontend/` Vue、`python-services/` 含 KG/RAG、Neo4j 图谱、Milvus 向量库）。已知隐患：现有实现可能为「壳子重、内核浅」的 demo，AI 生成的旧代码常「能跑但改不动」。

## 三、评估方法（四步法）

### 步骤 1 · 文档通读
接收并通读申报书、相关论文、参考项目说明、现有项目既有文档，建立「承诺功能清单」与「架构预期」。

### 步骤 2 · 模块映射
将代码模块逐一对齐至《决策对齐总表》的功能边界与红线，形成模块—决策对照矩阵，识别「应有而未有」与「有但偏离」。

### 步骤 3 · 完成度分级
对每个功能打标，四级：

| 等级 | 定义 | 判据 |
| --- | --- | --- |
| 生产级 | 可交付、可演示、可维护 | 端到端通、有测试、逻辑清晰可改 |
| Demo 级 | 表面可用、内核浅 | 仅happy path、缺边界与兜底 |
| 未实现 | 仅有入口或空壳 | 无核心逻辑 |
| 有漏洞 | 实现但存在缺陷 | 幻觉、错误诊断、不可溯源等红线风险 |

### 步骤 4 · 交叉挑刺
启用**评审子 Agent** 独立审查，专门挑战：① 图谱是否真实参与问答（红线一）；② 诊断是否真基于图谱（红线二）；③ 问答是否真命中知识库且防幻觉（红线三）；④ 旧码是否隐藏不可维护结构。评审子 Agent 须先输出「可能错在哪」再给结论，抑制顺从偏差。

## 四、交付物

评估完成后产出独立的《现有项目完成度与漏洞评估报告》，含：
1. 模块—决策对照矩阵；
2. 完成度分级清单（生产级 / Demo 级 / 未实现 / 有漏洞）；
3. 红线符合性结论；
4. 重构 vs 复用建议（服从「不默认旧码正确、劣构必改」原则）。

## 五、深度保证机制

- **不默认旧码正确**：任何旧实现均须经步骤 3 判据验证，未验证不继承。
- **评审子 Agent 独立通道**：与主实现 Agent 隔离，避免自我印证。
- **可溯源判据**：每项结论附带代码位置或运行证据，杜绝表面判断。
