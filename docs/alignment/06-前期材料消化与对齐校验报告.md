## 三、与基线01 / AGENT.md 的交叉校验

### 3.1 一致性确认（无冲突，已对齐）

- **三条不可破红线**：全部前期材料均支持真实图谱构建（杜彩丽 IPA/IREM、孟瑶瑶/LoRA+Neo4j、软件测试 Neo4j 均属真实图谱，非 prompt 假装），与基线01 红线①一致；RAG 防幻觉、可溯源（开题稿 L27「可解释性」、申报书 L371）与红线③一致。
- **差异化主张**：申报书 L147/L371、开题稿 L15 均强调「知识图谱结构化 + 降低幻觉 + 可解释」，与基线01 第五节一致。

- **技术路线 IPA/IREM**：开题稿 L25 与 PRD 术语一致，源自杜彩丽论文。
- **周期**：申报书 2026.4–2027.3 与基线01 演进路线一致。
- **AGENT.md 工程纪律**：互联网+ 十不准「不准虚假陈述/不准伪造数据」⇔ AGENT.md §1.5.4「AI 须指出错误不盲从」+ §1.5.5 红线；「不准核心工作外包代做」⇔ 团队须真实理解核心（与用户「暴露稳定 API + 有文档 + 你能独立部署」一致）。

### 3.2 冲突清单（标红＝待裁决）

> **C1｜图谱存储：Neo4j 还是关系表？**
> - 基线01 技术选型行（L24）：「**图谱存 Neo4j**」

> - PRD L187：「知识存储层：关系型业务表 + 知识图谱（**当前以关系表 knowledge_points / knowledge_point_relations 承载；Neo4j 为规划能力**）」
> - PRD L221：「**Neo4j、Milvus、Elasticsearch 为规划中的增强能力，尚未在现行版本强制落地**」
> - 申报书未锁定 Neo4j（仅「选择合适的知识图谱存储方案」）
> - **结论**：基线01 写法与 PRD 现行实现直接矛盾，且用户 Round6 回忆与 PRD 不符。

> **C2｜KG/RAG 实现语言：Python 还是 Java？**
> - 基线01 技术选型行（L24）：「**Vue + Python（队友 KG/RAG）+ Java（本人）**」

> - PRD L179：「**8001/8002 已由 Java 自包含实现接管，不调用 Python；8003 启用时调用**」
> - PRD L189：「RAG 引擎层：**Java 自包含检索**（Okapi BM25 召回…）、LLMProvider 调用、GraphRAG 增强」
> - **结论**：基线01 写法与 PRD 现行实现直接矛盾。可能的解释：队友原始 Python 实现已被 Java 自包含重写（架构演进），或用户回忆为演进前状态。

> **C3｜开题叙事 vs 现状（中风险，非硬冲突）**
> - 开题稿 L21/L27、PPT L102/L104/L70 将 **LoRA、FAISS、Neo4j** 以「系统模块 / 已构建」口吻陈述；
> - PRD L173/L195/L221 将其标为「**可选 / 规划 / 未强制落地**」。
> - 申报书未明示这些组件（保守，无冲突）。
> - **结论**：开题叙事领先于实现。结题/答辩若直接沿用开题措辞称其「已实现」将触碰互联网+ 十不准「不准虚假陈述」。须在结题材料中按实际落地状态诚实表述（可写「已规划/部分实现/实验性」）。

## 八、代码核验收口（2026-11-02，应「先查代码再定」）

经核查 `backend/`、`python-services/`、`docker-compose.yml`、`application.yaml`、SQL 迁移与种子，C1/C2 事实如下：

### C1｜图谱存储 = 双存储，均真实
- Java/MySQL 侧：`knowledge_points` / `knowledge_point_relations` / `chapter_knowledge_points` 表（V1 迁移 + V6《计算机网络》灌种 57 节点/关系），始终在线，为消费侧与兜底。
- Python `kg_service` 侧：`kg_store.py` 含 `Neo4jStore`（真实 Cypher `:Kp`/`:RELATES`，shortestPath 多跳）+ `MemoryStore` 双实现；`KG_BACKEND` = memory/neo4j/auto，auto 下 Neo4j 不可达回落内存。Neo4j 经由 docker-compose（profile rag）可选部署。
- `neo4j_fake.py` 仅为**测试替身**（test double，验证参数化/连接释放），非生产伪图谱，**不触红线①**。
- 结论：基线01「仅 Neo4j」片面；PRD「Neo4j 为规划能力」低估——Neo4j 已落地为可选真实后端。准确表述：双存储，关系表为主+兜底，Neo4j 可选真实后端。

### C2｜KG/RAG 引擎 = Python 主体（用户记忆正确），Java 仅消费侧+兜底
- `application.yaml`（L361-420）：`knowledge-graph.enabled=KG_ENABLED:false`、`rag.enabled=RAG_ENABLED:false` 默认关闭；Java 经 `HttpKnowledgeGraphProvider`（→8001）/ `HttpRagProvider`（→8002）HTTP 对接，启用时调用队友 Python 服务。
- 注释（L362-364/L386-388）明示：图谱引擎与 RAG 检索引擎「由团队另一成员负责，本端不再内置引擎实现，仅保留消费侧 + HTTP 代理 + 本地降级」。
- 禁用时走 `LocalKnowledgeGraphProvider`（本地 BFS）+ `DisabledRagProvider`（503→纯 LLM 降级）。
- 结论：PRD L179「8001/8002 已由 Java 自包含实现接管，不调用 Python」**有误**；基线01「Python（队友 KG/RAG）+ Java（本人）」**正确**。准确表述：Python 微服务是 KG/RAG 引擎主体，Java 为消费侧+兜底+HTTP 代理。
