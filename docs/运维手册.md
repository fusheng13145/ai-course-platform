> **架构详情见 `docs/架构手册.md`（系统定位、部署拓扑、逻辑分层、职责边界、技术栈、目录结构、核心设计决策、标准化集成层）。** 本节仅保留部署视角速览。

```
┌──────────┐     ┌──────────────┐     ┌────────┐     ┌───────┐
│  Nginx   │────▶│ Spring Boot  │────▶│ MySQL  │     │ Redis │
│  :80     │     │ :8080 (/api) │     │ :3306  │     │ :6379 │

监控与日志数据流（monitor profile，详见第 13 章）：
  Spring Boot ──/api/actuator/prometheus──▶ Prometheus(9090) ──rule_files──▶ Alertmanager(9093) ──webhook──▶ 通知渠道
       │                                                                              │
       └── docker 容器日志 ──▶ Promtail ──push──▶ Loki(3100) ──query──▶ Grafana(3000) ◀── Prometheus
```

- **前端**：Vue 3 + Element Plus，Nginx 反向代理，监听 80 端口

## 3. 快速部署

### 3.1 环境变量配置

```bash
# 1. 复制环境变量模板
cp .env.example .env

# 2. 编辑 .env，填入真实值（所有字段必须填写）
#    MYSQL_ROOT_PASSWORD - 强随机密码（≥16位）
#    JWT_SECRET         - 256位 Base64 随机字符串
#    DEEPSEEK_API_KEY   - DeepSeek API Key
```

**生成强密码**：
```bash
# Linux/Mac
openssl rand -base64 32

# Windows PowerShell
[System.Convert]::ToBase64String([System.Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
```

### 3.2 Docker Compose 部署（推荐）

```bash
# 启动所有服务（mysql + redis + backend + frontend；backend/frontend 归入 full profile）
docker compose --profile full up -d

# 仅启动基础设施（mysql + redis，供本地后端源码连接）
docker compose up -d mysql redis

# 启动全套 + 监控/告警/日志集中化（monitor profile：Prometheus/Grafana/Alertmanager/Loki/Promtail）
docker compose --profile full --profile monitor up -d --build

# 启动全套 + 每日自动备份（ops profile：mysql-backup 守护）
docker compose --profile full --profile ops up -d --build

# 监控 + 备份同时启用（三 profile 叠加）
docker compose --profile full --profile monitor --profile ops up -d --build

# 查看状态
docker compose ps

# 查看日志
docker compose logs -f backend
docker compose logs -f frontend
```

> 生产环境请在 `docker-compose.yml` 或 `.env` 中填充 `JWT_SECRET` / `DEEPSEEK_API_KEY` / `MAIL_*`；设置 `REDIS_PASSWORD` 后 Redis 容器自动启用 `--requirepass`（健康检查与后端 `SPRING_DATA_REDIS_PASSWORD` 同步生效），安全开关 `COOKIE_SECURE` / `REQUIRE_HTTPS` / `CSRF_ENABLED` 可经 `.env` 一键开启（详见 `.env.example` 注释）。

### 3.3 本地开发部署

> **完整本地开发指南（环境准备、启动方式、访问地址、常见问题）见 `docs/开发指南.md`。** 以下为速览。

**前置条件**：MySQL 和 Redis 已在本地运行。

```bash
# Windows
start-backend.bat    # 启动后端（:8080，自动激活 local 配置，含本地 DeepSeek Key）
start-frontend.bat   # 启动前端（:5173）

# Linux/Mac（手动）
cd backend && ./mvnw spring-boot:run -Dspring-boot.run.profiles=local
cd frontend && npm install && npm run dev
```

## 4. 健康检查

### 4.1 综合健康端点

| 端点 | 用途 |
|------|------|
| `GET /api/actuator/health` | 综合健康状态（DB + Redis + Disk + 自定义探针聚合；`show-details=when_authorized`，仅授权后泄露内部详情） |
| `GET /api/actuator/health/readiness` | K8s Readiness Probe |
| `GET /api/actuator/health/liveness` | K8s Liveness Probe |
| `GET /api/actuator/prometheus` | Prometheus 指标暴露端点（`/api/actuator` 前缀由 `context-path=/api` 决定） |

> **鉴权说明（重要，与旧版手册不同）**：`/api/actuator/prometheus` **不依赖 ADMIN 角色或业务 JWT**。监控体系第五轮起，该端点由一条独立的 Basic 鉴权链（`actuatorFilterChain`，`@Order(0)`）保护，凭据为监控专用账号 `APP_ACTUATOR_BASIC_USER` / `APP_ACTUATOR_BASIC_PASSWORD`（与业务 JWT 链路完全隔离）；口令留空时抓取 **fail-closed**（拒绝）。Prometheus 经 `basic_auth` 抓取样板，凭据须与 backend 的 `APP_ACTUATOR_BASIC_*` 完全一致。内网/演示无反向代理时，可置 `APP_ACTUATOR_SECURED=false` 放开抓取。

### 4.2 业务健康探针（子端点）

应用内置 4 个自定义 `HealthIndicator`，可单独探测各依赖（综合端点聚合其状态）：

| 子端点 | 探测对象 | 失败时含义 |
|--------|----------|-----------|
| `GET /api/actuator/health/database` | MySQL 连接与查询 | 数据源不可用，核心业务中断 |
| `GET /api/actuator/health/redis` | Redis PING | 缓存/会话/限流不可用（强依赖，启动即校验） |
| `GET /api/actuator/health/llmProvider` | LLM 供应商（DeepSeek/OpenAI/Qwen）连通性 | AI 问答/出题/批改等将失败 |
| `GET /api/actuator/health/pythonServices` | Python 微服务（微调 8003 等，启用时）连通性 | 微调能力不可用（RAG/KG 为预留接口，不在探针范围） |

### 4.3 监控组件端点（monitor profile）

启用 `--profile monitor` 后，下列组件对外暴露管理/查询界面（详见第 13 章）：

| 组件 | 端口 | 访问地址 | 说明 |
|------|------|----------|------|
| Prometheus | 9090 | `http://<host>:9090` | 指标查询、Targets、Alerts 状态 |
| Grafana | 3000 | `http://<host>:3000` | 看板（默认 admin/admin，**生产必须改口令**） |
| Alertmanager | 9093 | `http://<host>:9093` | 告警分发与静默管理 |
| Loki | 3100 | `http://<host>:3100` | 日志存储 API（通常经 Grafana 检索，不必直连） |

Docker Compose 已配置健康探针（实际值）：
- MySQL：`mysqladmin ping`，5s 间隔，20 次重试，start_period 30s
- Backend：`curl /api/actuator/health`，15s 间隔，12 次重试，start_period 60s

## 5. 日志分析

### 5.1 日志位置

| 环境 | 位置 |
|------|------|
| Docker | `docker compose logs -f <service>` |
| 本地开发 | 控制台输出 |

### 5.2 日志级别调整

生产环境默认 `INFO`。排查时可通过环境变量临时提级：

```bash
# 提级为 DEBUG（输出 SQL 和详细日志）
export LOG_LEVEL_COM_AICOURSE=DEBUG

# 重启后端服务
```

**注意**：DEBUG 级别会输出 SQL 语句和请求详情，生产环境勿长期开启。

### 5.3 关键日志模式

| 日志内容 | 含义 | 处理 |
|----------|------|------|
| `CSRF 校验失败` | 客户端缺少 XSRF-TOKEN | 确认前端 axios 配置 `withXSRFToken: true` |
| `Rate limit exceeded` | IP 请求过于频繁 | 检查是否有脚本/爬虫；调大 `ratelimit.*.limit` |
| `AI quota exhausted` | 用户 AI 调用配额用尽 | 调大 `ai.quota.daily-request-limit` 或等待次日重置 |
| `WebSocket 消息处理异常` | 客户端发送畸形数据 | WARN 级别，不影响服务，但需关注频率 |

### 5.4 集中化日志检索（Loki，monitor profile）

启用 `--profile monitor` 后，Promtail 自动采集 `aicourse-backend` 容器日志并推送至 Loki，可在 Grafana 的 Loki 数据源中检索，无需 `docker compose logs` 逐容器翻看：

- **Grafana 检索**：左侧 Explore → 选择 `Loki` 数据源 → 查询 `{container="aicourse-backend"}`；可按结构化 label 过滤：
  - `{container="aicourse-backend"} |= "ERROR"`（含 ERROR 文本行）
  - `{container="aicourse-backend"} | json | level="ERROR"`（按解析出的 level 字段过滤）
  - `{container="aicourse-backend"} | json | logger="com.aicourse.xxx"`（按 logger 下钻）
- **结构化字段**：Promtail 解析 Spring Boot 3.x 日志，提取 `level` / `logger` / `thread` / `message` / `timestamp` 为 Loki 索引/label，支持按级别与 logger 分组。
- **实时错误面板**：Grafana 看板「日志」组（第 13.5 节）内含「最近错误日志」实时面板，可与「告警概览」联动定位根因。
- **告警联动**：ERROR 日志速率突增由 `LogErrorSpike` 告警规则经 Alertmanager 推送（第 13.4 节），实现 Logs → Alerting 闭环。

## 6. 常见故障处理

### 6.1 后端启动失败

| 现象 | 可能原因 | 解决 |
|------|---------|------|
| `CommunicationsException: Communications link failure` | MySQL 未启动或密码错误 | 检查 MySQL 状态，确认 `.env` 中 `MYSQL_ROOT_PASSWORD` 正确 |
| `PatternParseException: Invalid mapping pattern` | springdoc 版本不兼容 | 已排除 `SwaggerConfig`，若仍出现检查是否引入了新版 springdoc |
| `JWT signature does not match` | JWT_SECRET 不一致 | 确保所有实例使用相同 `JWT_SECRET`（若 `start-backend.bat` 行尾被改写为 LF，会导致 JWT_SECRET 截断触发 WeakKeyException，务必保持 CRLF） |
| `RedisConnectionFailureException` | Redis 未启动 | 启动 Redis 或检查 `SPRING_DATA_REDIS_HOST` 配置 |

### 6.2 前端无法访问后端

| 现象 | 可能原因 | 解决 |
|------|---------|------|
| 跨域错误 (CORS) | 前端 origin 不在白名单 | 检查 `cors.allowed-origins` 配置 |
| 401 未授权 | Cookie 未携带或令牌过期 | 清除浏览器 Cookie 重新登录 |
| 403 CSRF 校验失败 | 前端 axios 未配置 `withXSRFToken` | 确认 `request.js` 中 `withXSRFToken: true` |

### 6.3 AI 功能不可用

| 现象 | 可能原因 | 解决 |
|------|---------|------|
| AI 问答返回"知识库原文" | `DEEPSEEK_API_KEY` 未配置 | 在 `.env` 中设置有效的 API Key |
| AI 调用超时 | 网络问题或 API 服务异常 | 调大 `AI_READ_TIMEOUT`，检查 `api.deepseek.com` 可达性 |
| `AI quota exceeded` | 用户当日调用次数/Token 超额 | 调大 `AI_QUOTA_DAILY_REQUESTS` / `AI_QUOTA_DAILY_TOKENS` |

### 6.4 数据库初始化（Flyway 自动迁移）

> **2026-08-30 起**：数据库迁移已由 Flyway 接管（`spring.flyway.enabled=true` + `baseline-on-migrate`），
> **无需再手动导入 index.sql**：
> - **全新部署（空库）**：后端启动时自动执行 `db/migration/V1__init_schema.sql`（48 表 + 种子数据，等价于原 index.sql）。
> - **已运行实例（曾手动导入 index.sql）**：Flyway 将非空库自动标为 baseline v1，V1 不重复执行，**数据不受影响**；后续版本以 `V2__xxx.sql` 增量演进。
> - 迁移脚本目录：`backend/src/main/resources/db/migration/`；V1 为 index.sql 的等价副本（剔除 `CREATE DATABASE/USE`，该职责由连接 URL / docker-compose 承担）。
> - 测试环境（test/local/contract-test profile）保持 `spring.sql.init` + index.sql 重建，不受影响。

```bash
# 兜底手动初始化（仅当 Flyway 迁移失败或需全量重建时）
docker exec -i aicourse-mysql mysql -uroot -p"${MYSQL_ROOT_PASSWORD}" ai_course_platform < backend/src/main/resources/index.sql
```

| 知识图谱 (8001) | 8001 | 引擎逻辑由团队另一成员负责；本端已实现消费侧（`KnowledgeController` 直读 MySQL `knowledge_points` / `knowledge_point_relations`）+ **标准化集成层**：`KnowledgeGraphContract` 接口 + `LocalKnowledgeGraphProvider`（默认本地 BFS 兜底）/ `HttpKnowledgeGraphProvider`（`knowledge-graph.enabled=true` 时按 `ContractPaths` 调 Python 8001 `/api/v1/graph/*`）；`POST /api/knowledge/path/plan` 在引擎未启用/不可达/未找到路径时由消费侧**本地 BFS 兜底**，始终返回真实数据 | **是（启用时）** | `knowledge-graph.enabled`（默认 `false`，`KG_ENABLED`）+ `knowledge-graph.base-url`（默认 `http://localhost:8001`） |

### 11.6 配置说明

Java 后端通过 `application.yaml` 控制服务地址，全部契约键（端点路径、请求/响应字段名、状态码与模式语义）统一由 Java 端 `com.aicourse.integration.ContractPaths` 常量定义（详见 `docs/集成契约-知识图谱与RAG.md` §3 / §6）。KG 与 RAG 的配置键均已被集成层实际消费（非预留）：

```yaml
# 知识图谱服务（引擎由团队另一成员负责；本端 KnowledgeGraphContract 接口 + 本地/HTTP 双实现，
# enabled=true 时由 HttpKnowledgeGraphProvider 调 Python 8001 /api/v1/graph/*；路径规划端点由消费侧本地 BFS 兜底）
knowledge-graph:
  enabled: ${KG_ENABLED:false}
  base-url: ${KG_BASE_URL:http://localhost:8001}
  connect-timeout: ${KG_CONNECT_TIMEOUT:5}
  read-timeout: ${KG_READ_TIMEOUT:30}
  max-retries: ${KG_MAX_RETRIES:2}
  health-path: ${KG_HEALTH_PATH:/api/v1/graph/health}
  rag:
    max-hops: ${KG_RAG_MAX_HOPS:2}

# RAG 服务（引擎由团队另一成员负责；本端 RagContract 接口 + 本地/HTTP 双实现，enabled=true 时调用 Python 8002）
rag:
  enabled: ${RAG_ENABLED:false}
  base-url: ${RAG_BASE_URL:http://localhost:8002}
  connect-timeout: ${RAG_CONNECT_TIMEOUT:5}
  read-timeout: ${RAG_READ_TIMEOUT:60}
  max-retries: ${RAG_MAX_RETRIES:2}
  default-top-k: ${RAG_DEFAULT_TOP_K:5}
  health-path: ${RAG_HEALTH_PATH:/api/v1/rag/health}

# LoRA 微调服务（启用时真实调用）
fine-tune:
  enabled: ${FT_ENABLED:false}
  base-url: ${FT_BASE_URL:http://localhost:8003}
  connect-timeout: 5
  read-timeout: 300
  max-retries: 1
  health-path: /api/v1/fine-tune/health
```

**环境变量覆盖：**
- `KG_ENABLED` — 知识图谱服务启用开关（默认 false；启用后本端 `HttpKnowledgeGraphProvider` 按契约调 Python 8001 `/api/v1/graph/*`；未启用时 `planLearningPath` 由消费侧本地 BFS 兜底）
- `KG_BASE_URL` / `RAG_BASE_URL` / `FT_BASE_URL` — 服务地址
- `RAG_ENABLED` — RAG 服务启用开关（默认 false；启用后本端 `HttpRagProvider` 按契约调 Python 8002 `/api/v1/rag/*`）
- `FT_ENABLED` — 微调服务启用开关（默认 false；启用后真实调用 Python 8003）

### 11.7 降级策略（当前实际行为）

| 场景 | 实际行为 |
|------|----------|
| 知识图谱路径规划（默认 / 引擎不可达 / 引擎未找到路径） | 消费侧本地 BFS 兜底（直读 `knowledge_point_relations`），始终返回真实路径；`mode=LOCAL`（未找到时 `found=false`） |
| 知识图谱 `ingest` / `getSubGraph`（引擎不可达） | 返回 `503` 占位（`mode=UNAVAILABLE`） |
| RAG 未启用（`rag.enabled=false`，默认） | 所有方法返回 `503` 占位（`DisabledRagProvider`，`mode` 缺省） |
| RAG 启用但不可达 / 调用失败 | 返回 `503` 占位（`mode=UNAVAILABLE`）；`AIServiceImpl.ragAsk` 检测到 `code:503` 自动回退为纯 LLM 调用 |
| 微调服务（8003）未启用/不可用 | `LLMFineTuneServiceImpl` 返回 `{"error":"微调服务暂不可用","code":503}` |

> 状态码与模式语义统一见 `docs/集成契约-知识图谱与RAG.md` §6；`ENGINE` 表示由 Python 引擎返回，`LOCAL` 表示本端本地兜底，`UNAVAILABLE` 表示不可用仅占位。

## 13. 监控、告警与日志体系

> 本章覆盖自监控体系第一轮（审计修复）至第七轮（Logs→Alerting 闭环）建设的全部运维产物。目标是把平台从「能跑」提升到「可观测、可告警、可下钻」。
> 全部组件均经 `docker compose` 的 `monitor` / `ops` profile 按需启用，**零侵入业务代码**（仅基础设施编排与配置文件）。

### 13.1 启用方式

监控与日志组件**默认不启动**，须显式叠加 profile：

```bash
# 全套业务 + 监控/告警/日志集中化（推荐生产观测基线）
docker compose --profile full --profile monitor up -d --build

# 仅监控基础设施（不含业务容器，供对接已有 backend）
docker compose --profile monitor up -d --build

# 监控 + 每日自动备份叠加
docker compose --profile full --profile monitor --profile ops up -d --build
```

> 未启用 `monitor` 时，Prometheus/Grafana/Alertmanager/Loki/Promtail **不会创建**；业务容器（backend）自身仍暴露 `/api/actuator/*` 端点，可被任意兼容 Prometheus 抓取（需按 13.6 配置鉴权）。

### 13.2 组件与端口

| 组件 | 镜像 | 端口 | 角色 | 配置文件 |
|------|------|------|------|----------|
| Prometheus | `prom/prometheus:v2.53.0` | 9090 | 指标抓取 + 规则评估 + Alertmanager 分发 | `prometheus/prometheus.yml` + `prometheus/alert_rules.yml` |
| Alertmanager | `prom/alertmanager:v0.27.0` | 9093 | 告警路由/静默/通知 | `prometheus/alertmanager.yml` |
| Grafana | `grafana/grafana:11.2.0` | 3000 | 看板可视化 | `grafana/provisioning/*` |
| Loki | `grafana/loki:2.9.8` | 3100 | 日志存储 | `loki/loki-config.yaml` |
| Promtail | `grafana/promtail:2.9.8` | （内部 9080，不对外映射） | 日志采集→Loki | `loki/promtail-config.yaml` |

> Promtail 经 Docker socket（`/var/run/docker.sock:ro`）服务发现 `aicourse-backend` 容器，**不改应用日志格式**、不引入 Maven 依赖，仅本地 Docker 环境可用（Docker 桌面默认提供 socket）。

### 13.3 指标来源

Prometheus 抓取 `backend:8080/api/actuator/prometheus`，指标分三类：

1. **框架默认**：`http_server_requests_seconds_*`（已启用 histogram，支撑 P99 延迟）、`jvm_memory_*` / `process_cpu_usage`（micrometer 自动注册）、`up`（抓取存活）。
2. **业务自定义（`aicourse_*`）**：
   - 业务计数（11 个 Gauge，`BusinessMetricsService` 每 60s 刷新）：`aicourse_courses` / `aicourse_enrollments` / `aicourse_active_students` / `aicourse_teachers` / `aicourse_submissions` / `aicourse_pending_submissions` / `aicourse_exams` / `aicourse_questions` / `aicourse_wrong_questions` / `aicourse_learning_records` / `aicourse_discussions`。
   - AI 调用（按 8 类分桶 `chat/question/content/correct/rag/recommend/analyze/extract_graph`）：`aicourse_ai_calls_total{type}` / `aicourse_ai_tokens_estimate_total{type}`（输入字符数 ÷ 1.5 折算，演示口径）/ `aicourse_ai_calls_failed_total{type}`。
   - 作业提交：`aicourse_submissions_created_total`。
   - 维度下钻 Gauge：`aicourse_course_*`（带 `course`/`course_name`/`teacher`/`teacher_name` 标签，5 指标）/ `aicourse_classroom_*`（带 `class`/`class_name` 标签，4 指标）。
3. **日志派生指标**（Promtail → Prometheus）：`promtail_custom_log_lines_total{level}`（按日志级别计数，支撑错误日志突增告警）。
4. **业务依赖健康指标**（`HealthMetricsService` 每 60s 刷新，将 `/actuator/health` 探针状态化为指标）：`aicourse_health_status{component}`（component ∈ {database, redis, llmProvider, pythonServices}；取值 1=UP / 0=DOWN / 0.5=UNKNOWN·未启用，支撑业务依赖存活告警）。

> 维度 Gauge 由 `@Scheduled(60s)` 首采，容器启动后约 1 分钟指标与看板模板变量值陆续出现；Counter 仅统计应用启动后的事件。

### 13.4 告警规则与阈值

规则定义在 `prometheus/alert_rules.yml`，分 9 组（共 13 条，均带 `severity` 标签与中文 runbook 注释）：

| 分组 | 告警名 | 触发表达式（摘要） | for | severity |
|------|--------|-------------------|-----|----------|
| aicourse-availability | `BackendDown` | `up{job="aicourse-backend"} == 0` | 1m | critical |
| aicourse-http | `HttpErrorRateHigh` | 5xx 错误率 > 5% | 5m | warning |
| aicourse-http | `HttpErrorRateCritical` | 5xx 错误率 > 20% | 2m | critical |
| aicourse-http | `HttpP99LatencyHigh` | P99 延迟 > 2s | 5m | warning |
| aicourse-jvm | `JvmHeapUsageHigh` | 堆使用率 > 85% | 5m | warning |
| aicourse-jvm | `JvmHeapUsageCritical` | 堆使用率 > 95% | 2m | critical |
| aicourse-business | `PendingSubmissionsBacklog` | 待批改数 > 200 | 10m | warning |
| aicourse-ai | `AiFailureRateHigh` | AI 失败率 > 20% | 5m | warning |
| aicourse-logging | `LogErrorSpike` | ERROR 日志速率 > 0.5/s | 5m | warning |
| aicourse-meta-monitoring | `MonitoringComponentDown` | 任一监控组件 up==0 | 1m | critical |
| aicourse-dependencies | `HealthDependencyDown` | 业务依赖健康分 min==0 | 1m | critical |
| aicourse-host | `HostDiskUsageHigh` | 宿主机磁盘使用率 > 85% | 5m | warning |
| aicourse-host | `HostDiskUsageCritical` | 宿主机磁盘使用率 > 95% | 2m | critical |

> **阈值均为演示初值**，生产须按真实容量压测后调整（见 13.7）。告警经 Alertmanager 统一路由，`aicourse-logging` 组的 `LogErrorSpike` 复用同一链路，避免引入第二个告警引擎（Logs 与 Metrics 双引擎闭环）。

### 13.5 Grafana 看板

预置看板 `grafana/provisioning/dashboards/aicourse-backend.json`（**39 个面板**），含模板变量实现联动下钻：

- **模板变量**：`$datasource`（数据源切换）、`$course` / `$classroom` / `$teacher`（课程/班级/教师动态下拉，`multi + includeAll`）、`$unit_cost`（AI 成本参考单价，默认 0.0005 元/token ≈ 0.5 元/千 token）。
- **面板分组**：业务概览（11 统计卡 + 待批改占比）、AI 调用类型分析、课程维度下钻（Top10）、班级维度下钻（Top10）、**告警概览**（即时查 `ALERTS{alertstate="firing"}`，直接反映 13.4 规则真实触发状态，与 Alertmanager 分发解耦）、AI 调用失败率（按类型）、日志（日志量按级别 / ERROR-WARN 速率 / 最近错误日志实时 / 总吞吐）、**监控组件存活（/5）**（stat，sum(up) 反映监控链路自身健康）、**业务依赖健康（最小）**（stat，min(aicourse_health_status) 反映 DB/Redis/LLM/Python 依赖可用性）。

### 13.6 配置与通知渠道

相关 `.env` 变量（详见 `.env.example`）：

| 变量 | 默认 | 说明 |
|------|------|------|
| `APP_ACTUATOR_BASIC_USER` / `APP_ACTUATOR_BASIC_PASSWORD` | `monitor` / 空 | 监控端点 Basic 鉴权账号；**口令留空则 Prometheus 抓取 fail-closed**。须与 Prometheus 容器透传值一致 |
| `APP_ACTUATOR_SECURED` | `true` | 监控端点鉴权总开关；内网/演示无反向代理时可置 `false` 放开抓取 |
| `GRAFANA_ADMIN_USER` / `GRAFANA_ADMIN_PASSWORD` | `admin` / `admin` | **生产必须修改**，严禁默认弱口令上线 |
| `ALERTMANAGER_WEBHOOK_URL` | 空 | 告警通知 webhook（企业微信/钉钉/飞书机器人等）；留空则告警仅在 Prometheus/Alertmanager UI 可见、不主动推送 |
| `BACKUP_RETENTION_DAYS` | `14` | 仅 `ops` profile 的 mysql-backup 使用 |

> 可选邮件通知：取消 `prometheus/alertmanager.yml` 中 `email-admin` 接收器注释并配置 `SMTP_*` 变量。

### 13.7 生产运维建议

1. **阈值压测校准**：`PendingSubmissionsBacklog > 200`、`AiFailureRateHigh > 20%`、`LogErrorSpike > 0.5/s` 等均为演示初值，须按真实业务量级（并发、班级规模、AI 调用频率）压测后调整。
2. **监控组件自身可用性（meta-monitoring）**：当前未抓取 Prometheus/Alertmanager/Loki 各自的 `/metrics`，建议补充 `MonitoringComponentDown` 告警，避免「监控组件宕机无人知晓」。
3. **日志长期留存**：Loki 单实例 filesystem 卷受本地磁盘约束；长期审计归档建议改用 S3/MinIO 对象存储后端。
4. **链路追踪（Tracing）**：当前单体架构下价值有限；若后续拆分为微服务，可补 OpenTelemetry + Tempo 补齐可观测性第三支柱。

### 13.8 常见故障排查

| 现象 | 排查方向 |
|------|----------|
| Prometheus Targets 中 `aicourse-backend` 为 DOWN | 检查 `APP_ACTUATOR_BASIC_*` 与 Prometheus 容器透传值是否一致；`APP_ACTUATOR_SECURED=true` 时口令不可为空 |
| Grafana 看板无数据 | 确认 datasource provisioning 成功；维度 Gauge 容器启动后约 1 分钟才出现；检查 `$course` 等变量是否选到有效值 |
| 告警触发但无通知 | 检查 `ALERTMANAGER_WEBHOOK_URL` 是否配置；在 Alertmanager UI（:9093）查看 `Alerts` 与 `Silences` 状态 |
| Loki 检索无日志 | 确认 Promtail 容器已启动且挂载了 Docker socket；查询语法用 `{container="aicourse-backend"}`（container label 由 Promtail 解析赋值） |
| Grafana 无法登录 | 凭据为 `GRAFANA_ADMIN_*`，非 backend 账号；默认 admin/admin 仅限首次，生产须改 |
