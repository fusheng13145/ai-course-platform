## 1. 形态可行性评估（独立软件 / 网站 / 小程序）

| 形态 | 可行性 | 适用场景 | 复用度 / 改造量 | 结论 |
| --- | --- | --- | --- | --- |
| 多租户 Web SaaS（网站） | ★ 可行（最优） | 高校 / 培训机构多租户教学、社会培训、个人自学订阅 | 后端逻辑复用 80%+；需加租户隔离 / 计费 / 配额；flowcontrol 可扩为租户配额 | **主形态** |
| 微信小程序 | 可行 | C 端轻触达：查课表 / 成绩 / 刷题 / 通知；重考试防作弊不适合 | 后端 REST 复用；前端 uni-app / Taro 重写；加 code2session 桥接、临时文件上传、订阅消息；HttpOnly Cookie → 小程序登录态 + Bearer | **轻量入口** |
| 桌面软件（独立软件） | 可选（低优先） | 高校内网一体机（离线 / 内网管控） | Tauri 打包前端 Vue + 内网后端；考试 / AI 判分 / 防作弊强依赖服务端，离线价值低 | 非首选 |

**判定**：以「多租户 Web SaaS 为主形态 + 微信小程序为轻触达渠道」；桌面软件仅在特定内网场景作为可选交付。

### 优劣对比

- **Web SaaS**：开发成本最低（复用现有 Spring Boot + Vue）、分发最易（URL + 子域名）、易做多租户与计费；劣势是需自建运维 / 合规 / 客服体系。
- **微信小程序**：触达成本低（微信生态）、适合轻量学习；劣势是平台审核约束、不能承载重考试防作弊、需额外登录态改造（F-19）。
- **桌面软件**：满足内网 / 离线管控；劣势是离线价值低（核心 AI / 判分 / 防作弊依赖服务端）、分发与升级成本高。

## 4. 整体架构（多租户改造）

4.1 **数据层**：行级隔离 `tenant_id` + 租户上下文拦截器（MyBatis `TenantLineInnerInterceptor` 自动注入）；schema 隔离为备选（依合规 / 规模定）。
4.2 **认证层**：API 网关签发 **tenant-scoped JWT**（claim 含 tenantId）；小程序走微信 `code2session` 换自有 token，弃 HttpOnly Cookie 单租户假设。
4.3 **部署**：K8s + RDS(MySQL) + 对象存储（MinIO / OSS）；配额复用 Sentinel(flowcontrol)。
4.4 **复用**：Spring Boot + Vue 不变；Python KG / RAG 微服务保持契约对接（手册第八部分）。
   > 2026-10-06 更新：两引擎已**不再是占位骨架**——`kg_service`(:8001) 11 个端点 + Neo4j 图存储（`:Kp` 标签，未连通时回退内存图），`rag_service`(:8002) 9 个端点 + BM25/向量/RRF 检索；Java 侧以 `ContractPaths`（55 个契约常量）为唯一路径来源。产品化的租户维度接入只需在契约层加 `tenantId`，不必重写引擎。
   > 仍缺：`:8003` LoRA 微调无 Python 实现（DR-23）；两引擎的 Dockerfile 暂缓，故**尚无容器化交付物**，K8s 部署需先补镜像。
4.5 **小程序端**：uni-app 重写轻端；临时文件上传 + 订阅消息；重考试防作弊仍在 Web 端。

> ⚠️ 当前代码库为**单租户**（2026-10-06 复验：`grep -rli tenant backend/src/main/java` **仍零命中**，48 张表无 `tenant_id` 列），M1 多租户隔离为**从零引入**，工期与优先级最高（见第 6 节安全验收）。

## 5. 安全验收门槛（产品化高优先级，来自 2026-09-14 安全审计交叉增补）

- **F-18（🔴）多租户隔离**：`TenantLineInnerInterceptor` 全局注入 + `tenantId` claim 强制 + 缓存 key 加租户前缀 / 命名空间隔离（与 F-17 缓存跨租户泄露合并为**单一工作项**）。任一遗漏 = 跨租户越权，M1 必须验收通过。
- **F-19（🟠）小程序 token 改造**：`session_key` 绝不下发 / 入日志；自有 Bearer 短 TTL 绑 openid；微信 `access_token` 仅服务端持有。任一遗漏 = 中-高伪登录 / 越权，M3 验收。
- 其余既有项：F-01 静态资源 ACL、F-09 XSS、F-14 CORS 已修复并复验（`docs/端到端验证与缺陷修复总报告.md` §二）；**F-02 密钥治理已完成应用侧接管点**，产品化阶段仍需把各租户密钥接入 Secret Manager（`docs/密钥注入与Secret管理.md`）。

## 6. 开发规划路线

- **M1 多租户数据隔离 + 租户上下文（最高优先级，从零引入）**
  - `TenantLineInnerInterceptor` + `tenant_id` 行级；租户上下文拦截器 / ThreadLocal。
  - 缓存租户隔离（F-17 / F-18 合并工作项）。
  - 单测固化隔离与跨租户拒绝。
  - **安全验收：F-18 通过。**
- **M2 认证 / 计费 / 配额**
  - 网关 tenant-scoped JWT；小程序 `code2session` 桥接（F-19 验收）。
  - 配额复用 flowcontrol(Sentinel)；计费台账。
- **M3 微信小程序轻端**
  - uni-app 重写；课表 / 成绩 / 刷题 / 通知；临时文件上传 + 订阅消息。
  - **安全验收：F-19 通过。**
- **M4 桌面一体机（可选）**
  - Tauri 内网打包前端 + 内网后端；离线管控场景。

## 7. 风险与待确认

- **MySQL 版本**：~~compose 8.0 与手册声明 8.4 不统一~~ **已闭合（CMP-1）**：`docker-compose.yml:33`（mysql）与 `:251`（mysql-backup）均为 `mysql:8.4`。⚠️ 但 `.github/workflows/ci.yml` 的 service 容器仍为 `mysql:8.0`，即**CI 校验的 Flyway 方言与生产/编排版本不同**；运行时端到端复核（`docker compose up` 跑一次 Flyway）在本机无 Docker daemon，仍未做。
- **消息队列**：**已确认 compose 无 MQ**（2026-10-06 复核：12 个服务为 mysql / redis / backend / frontend / mysql-backup / prometheus / node-exporter / alertmanager / grafana / loki / promtail / neo4j，全仓无 rabbitmq / kafka / activemq / nats）。通知重试与异步判分目前依赖应用内实现，M2/M3 若需可靠投递须**新增决策**（引入 MQ vs 用 Redis 队列 + 幂等表）。
- **Flyway 富种子脚本随镜像自动执行**（🔴 上线阻塞项，手册 DR-18）：`flyway.enabled=true` 且 prod 无覆盖，全新 SaaS 库首启即写入 V5/V6 的 162 个 `123456` 号段账号。多租户改造前须先落到构建期剔除或部署后按号段处置——**租户开通流程必须假定"演示数据不进生产"**。
- **微调能力无引擎实现**：`:8003` LoRA 微调在 Java 侧有契约常量与降级路径，但**无任何 Python 实现**（手册 DR-23）。若按「AI 调用量计费」设计商品项，微调暂不可纳入可售能力。
- **密钥供给形态**：SaaS 下 `DEEPSEEK_API_KEY` / `NEO4J_PASSWORD` 等须进 Secret Manager；应用侧接管点与三套接线方案见 `docs/密钥注入与Secret管理.md`（注意其 §2.2 的文件名精确匹配规则；接线件键名缺陷 DR-24 已于 2026-10-06 修正，端到端联通验证为残项）。
- **隔离策略**：行级 vs schema 依合规（教育个人信息保护）与数据规模定。
- **AI / 邮件凭据**：SaaS 下按租户或平台级供给，成本模型待定（`DEEPSEEK_API_KEY` 目前**任何环境都未注入**，AI 商品项的前置条件尚未满足）。
- **合规**：个人信息最小必要、加密、审计（等保 / 教育数据合规）。
