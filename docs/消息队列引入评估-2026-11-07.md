# 消息队列引入评估（2026-11-07 · 技术债立项评审稿）

> 背景：`docs/系统架构设计.md` §12 技术债表登记「无消息队列」；PRD §7.3 风险表记
> 「Phase 1 需评估是否引入可靠队列」。本文按企业立项口径给出评估结论与分期建议，
> **只做评审依据，不构成已实现能力**。

## 一、当前异步化的真实水位

| 链路 | 现状 | 风险 |
| --- | --- | --- |
| 通知扇出（公告 WP8 / 事件驱动 NotificationServiceImpl） | 同步循环逐人落库 + 逐人 WebSocket 推送，包在发布事务里 | 大班额（300+ 人）发布公告时事务内 N 次 insert + N 次 ws push，发布接口时延随时长线性涨；推送失败已 try/catch 隔离，但**落库失败会回滚整个发布** |
| AI 调用 | 同步阻塞（RestClient），Sentinel URL 级流控 + AiQuotaInterceptor 日配额兜底 | 长任务占 Tomcat 线程（500 线程池）；出题/批改高峰排队依赖线程池余量 |
| 定时任务 | ShedLock 防重入的 @Scheduled（考试超时、数据维护） | 单实例内串行；多实例靠锁竞争，无任务队列 |
| 邮件（验证码/重置） | 同步 SMTP | SMTP 抖动直接反映为接口时延 |
| 微调任务 | Python 8003 内部任务状态机（单 worker） | 与 Java 侧解耦已成立，不受本议题影响 |

## 二、候选方案对比

| 方案 | 引入成本 | 运维成本 | 适配度 | 结论 |
| --- | --- | --- | --- | --- |
| **Redis Stream + 消费者组**（Spring Data Redis 已在依赖内） | 低：新增 2 个 consumer 组件 + 发布侧投递工具类，无新中间件 | 低：复用现有 Redis（已强依赖 + fail-fast 校验） | 高：通知扇出、邮件投递、AI 任务削峰均为"轻负载、可容忍秒级延迟"场景 | **推荐 Phase 1 采用** |
| RabbitMQ | 中：新中间件 + 镜像 + 监控接入 | 中：持久化/镜像队列运维 | 高但过剩 | Phase 2（多实例规模化后再评） |
| Kafka | 高 | 高（ZK/KRaft、分区运维） | 过剩：当前无日志流/大吞吐诉求 | 不采用 |
| 进程内 @Async + 阻塞队列 | 最低 | 无 | 不解决可靠性（重启丢任务）与多实例路由 | 仅适合非关键旁路（如埋点落盘） |

## 三、建议分期（若立项）

**Phase 1a（1–2 人日，收益最大）**：通知扇出改投递 Redis Stream。
- 发布事务只落 `announcements` + 一条 `notify:fanout` 消息；消费者组按批次批量 insert notifications + ws 推送。
- 失败重试：消费者 `XACK` 前置 + 死信流（`notify:dead`）+ 现有 14 条监控告警体系加 `stream lag` 告警。
- 幂等键：`announcementId` 已可去重（notifications 可按 data.announcementId 查重）。

**Phase 1b（2–3 人日）**：验证码/重置邮件走同一 Stream（第二 consumer），SMTP 失败退避重投。

**Phase 2（待真实容量数据）**：AI 出题/批改长任务异步化（任务表 + Stream + 前端轮询改订阅）。触发条件：目标环境压测显示 AI 端点 P99 > 5s 或线程池饱和事件出现。在此之前 Sentine 流控 + 日配额已覆盖容量风险。

## 四、不引入队列的底线护栏（维持现状的前提下必须保持）

1. 通知扇出批量 insert（batchSendNotifications 已是）+ ws 推送逐条隔离（已是）——发布接口在大班额下的时延上限需在压测中实测留档。
2. AI 日配额（AiQuotaInterceptor）与 Sentinel 流控不得放松。
3. 所有"将要异步化"的链路在异步化前必须有降级读数（可观测），防止"换成队列后丢了却没人知道"。

## 五、结论

**Phase 1 不引入独立消息中间件；以 Redis Stream 做轻量可靠队列，仅异步化通知扇出与邮件两条链路。**
该结论与 ≥10,000 注册用户的单租户设计容量匹配，且不新增运维面。是否执行 Phase 1a 由项目主在上线批次排期中拍板（建议放在压测之后、扩班额使用之前）。
