## 一、功能完整性 【85/100 · A-】 权重25%

### 当前状态

后端 40 个 Controller、47 个实体/表、50 Service Impl；前端 65 个页面 + 34 个 API 模块。三端（管理员/教师/学生）路由隔离完整实现。核心功能（认证、课程、考试、AI 对话、知识图谱、学习路径、作业、查重、数据分���、WebSocket）均已实现并接通真实业务逻辑。

### 存在的具体问题

**1.【严重】3 个已知端点仍为占位/桩实现**

根据项目自查文档 + 代码确认：
- `GET /api/submissions/{id}/plagiarism`：返回引导文本「请使用 POST /check-plagiarism 触发查重」，非真实查重结果。尽管后端有完整的 `PlagiarismCheckServiceImpl`（Jaccard 相似度引擎），但该 GET 端点未接入它。
- `GET /api/learning-paths/generate`：返回 4 个硬编码主题词，未接入 AI 与数据库。注意：真正的 `POST /api/ai/learning-path/generate` 已完整实现（双算法：任务点驱动 + 知识点驱动），但该 GET 遗留端点未清理。
- `POST /api/knowledge-points/path/plan`：读取 `startPointId` 但未使用，仅按 `targetPointId` 计算前置知识点，属于演进中的部分实现。

**2.【中等】遗留 @Deprecated 接口未清理**
AIController 中 5 个端点标记 `@Deprecated(forRemoval=true)`：
`/ai/chat`、`/ai/generate-question`、`/ai/generate-summary`、`/ai/check-plagiarism`、`/ai/rag/ask`
这些接口仍常驻代码，增加维护负担，且前端部分页面仍有可能引用旧接口。

**3.【中等】前端 KnowledgeManagement.vue 含兜底假数据**
`generateFallbackExtraction()` 在 AI 不可用时本地构造示例知识点展示。文档注明「仅展示不入库」，但用户侧感知到的是假数据，且在离线演示中可能误导。

**4.【轻微】催交提醒、视频学习模块仅建表未实现功能**
表结构（reminders、learning_records.type=VIDEO）已存在，但无对应的定时任务或视频播放追踪逻辑。

### 可操作建议
1. **P0** 将 3 个桩端点改接真实引擎（plagiarism GET 复用 PlagiarismCheckService，learning-paths/generate 删除或转发到真实接口，path/plan 补全 startPointId 逻辑）
2. **P1** 删除或重写 `@Deprecated` 旧接口，前端统一迁移到新 API
3. **P1** 移除 `generateFallbackExtraction()`，AI 不可用时直接显示空状态提示
4. **P2** 实现催交定时任务和视频播放追踪（对应表结构已完备）

## 二、代码质量 【80/100 · B+】 权重15%

### 当前状态

整体代码风格统一，命名规范，分层清晰。后端无 `e.printStackTrace()`、无 `System.out.println()`、无裸 `return null` 模式。前端 logger.js 统一管理日志输出。TypeScript 启用 `strict: true`。

### 存在的具体问题

**1.【中等】手动拼接 JSON 代替 @JsonProperty 序列化**
`PlagiarismCheckServiceImpl.java` 的 `buildCheckDetailJson()` 方法手动拼接 JSON 字符串（`json.append("...")`），而非使用 ObjectMapper 或 Jackson 注解。易出现转义/格式错误，且无法经静态类型检查。类似的模式在 `RAGServiceImpl.java` 中也存在（手动 `toJson()` 回退）。

**2.【中等】部分 Service Impl 的循环依赖（@Lazy 修补）**
`RAGServiceImpl` 通过 `@Lazy` 注入 `KnowledgePointService` 以打破与 `AIServiceImpl` 的构造期循环依赖，表明模块间存在设计级别的耦合问题。

**3.【中等】前端大量使用 .js 而非 .ts（类型安全不足）**
尽管 tsconfig 启用了 `strict: true`，但 frontend/src/ 下大量文件为 `.js` 而非 `.ts`（路由、API 模块、多数页面）。仅 types.d.ts 提供类型声明但没有在 `.js` 文件中获得编译期类型检查收益。

**4.【轻微】异常日志不够精细化**
多处 `log.warn("XXX失败: {}", e.getMessage())` 只记录了 message 而非完整堆栈（`e`），生产排障时难以定位问题根源。

**5.【轻微】Magic Number / 字符串**
配置文件中存在少量不易读的数字（如 `estimatedTime: 30`、`每天按2小时学习计算`），虽影响不大但可提取为配置项。

### 可操作建议
1. **P0** 将 `buildCheckDetailJson` 改为 Jackson 序列化（已有 ObjectMapper 注入）
2. **P1** 重构循环依赖设计（AIServiceImpl → RAGServiceImpl → KnowledgePointServiceImpl → AIServiceImpl），引入事件驱动或中间层
3. **P1** 推进前端渐进式 TypeScript 化，至少覆盖 API 层和 stores
4. **P2** 全局审计异常日志，确保 `log.error` 输出完整堆栈

## 三、架构设计 【88/100 · A-】 权重15%

### 当前状态

标准三层架构（Controller → Service → Mapper），ArchUnit 架构测试已落地（5 条规则：Controller 不得依赖 Mapper、Service 不得依赖 Controller、Entity 须为纯数据载体等）。`LLMProvider` 接口抽象实现多供应商热切换。角色权限三端隔离。

### 存在的具体问题

**1.【中等】RAG 服务的架构定位模糊**
RAG 原设计为独立 Python 微服务（端口 8002），但已改为 Java 自包含实现（TF-IDF + 余弦），而 application.yaml 中仍保留 `rag.base-url`、`rag.health-path` 等面向 HTTP 远程调用的配置项以及 `PythonServicesHealthIndicator`（引用了 RAG 的 healthPath）。新旧架构配置并存，造成认知混淆。

**2.【中等】远程 Python 微服务的容错机制残缺**
`PythonServicesHealthIndicator` 对 Knowledge Graph(8001) 和 LoRA(8003) 的健康检查用了 `try-catch` 静默吞异常，返回 `Health.down()`。这意味着这些服务如果根本未部署，系统虽可运行但永远处于 degraded 状态而无告警。

**3.【轻微】DTO/VO 与 Entity 层复用**
部分 Controller 直接返回 Entity 对象而非 DTO/VO，导致 API 响应结构受实体字段影响（如 JSON 序列化时包含 `deleted`、`password` 等不应暴露的字段）。

### 可操作建议
1. **P1** 清理 RAG 旧配置项，统一为自包含实现的配置体系
2. **P1** 为 Python 服务降级添加显式告警（日志 + 通知）
3. **P2** 引入 DTO/VO 层隔离实体与 API 响应

## 四、性能表现 【78/100 · B+】 权重10%

### 当前状态

Redis 缓存已启用（@Cacheable，5分钟 TTL）、Gzip 压缩开启、Tomcat 线程池调优（max=500）、AI 调用异步化（Callable + 专用线程池 + CallerRunsPolicy + 120s 超时）。

### 存在的具体问题

**1.【中等】RAG 检索无缓存预热/索引**
每次 `ask()` / `retrieve()` 调用都实时加载知识点全表、实时词频分析、实时 TF-IDF 计算。课程知识点较多时（>1000 条），每次检索 O(N) 的词频向量化 + O(N×M) 的余弦距离计算，延迟可能到数百毫秒以上。尽管 `@Cacheable` 可缓解重复查询，但同一课程不同问题的首次查询仍是全量计算。

**2.【中等】无数据库查询分页兜底**
部分 Service 层查询（如 `loadCorpus`、`getStudentPaths`）未设置查询上限或分页，在大数据量下可能 OOM 或拖垮数据库。

**3.【轻微】前端 bundle 体积未优化**
未使用 `vite build --report` 分析，未做组件级懒加载拆分（路由懒加载已有，但部分页面可能引入大量 ECharts 等重依赖）。

### 可操作建议
1. **P1** RAG 增加 TF-IDF 向量缓存（courseId 维度）或定时重建索引
2. **P1** 全局审计无分页查询，添加 `last("LIMIT N")` 兜底
3. **P2** 添加构建体积分析，按需引入 ECharts 组件

## 五、安全性 【92/100 · A】 权重15%

### 当前状态

**这是项目中表现最好的维度。** 完整的安全纵深防御体系：
- BCrypt 密码加密 + JWT 认证 + HttpOnly Cookie（防 XSS 窃取令牌）
- RBAC + `@PreAuthorize` + URL 级安全规则
- CSRF 双提交 Cookie 防护（DoubleSubmitCsrfFilter）
- IP 级限流（登录 10次/60s、AI 20次/60s）
- AI 调用用户级配额（100次/天/用户）
- HSTS + CSP + X-Frame-Options + 防 MIME 嗅探
- 可配置 HTTPS 强制、Actuator 端点隔离
- 输入校验（spring-boot-starter-validation）
- 前端 DomPurify 防 XSS
- Prompt 注入检测（PromptGuard）

### 存在的具体问题

**1.【中等】默认演示账号及弱口令**
5个学生 + 2个教师 + 1个管理员密码均为 `123456`，虽然在 README 中明确标注了生产环境须更改，但 seed 脚本默认注入即存在安全风险。

**2.【中等】index.sql 中含测试邮箱明文**
seed 数据使用 `123456@qq.com` 和固定邮箱格式，生产环境若未替换可能招致邮件滥用。

**3.【轻微】应用信息泄露风险**
`/actuator/info` 公开（permitAll）会暴露 Maven 版本信息，虽信息量有限但构成信息泄露面。

### 可操作建议
1. **P1** seed 数据使用随机初始化密码（启动时生成不重复哈希）
2. **P1** seed 数据邮箱改用占位符 `user{id}@example.com`
3. **P2** 考虑将 `/actuator/info` 也纳入认证保护

## 六、可维护性 【82/100 · B+】 权重10%

### 存在的具体问题

**1.【中等】数据库初始化脚本不可重复执行**
`index.sql` 无幂等性保护（`CREATE TABLE IF NOT EXISTS` 未统一使用）。多次运行可能导致数据重复或报错。

**2.【中等】依赖项版本未集中到 BOM**
`pom.xml` 中第三方依赖版本通过 properties 管理（MyBatis-Plus 3.5.7、jjwt 0.12.6 等），但部分 Spring Boot 生态依赖未显式指定版本，依赖传递机制可能引入不一致。

**3.【轻微】前端 index.html 标题为默认值**
`frontend/index.html` 的 `<title>` 仍为默认的 `Vite App`，未改为项目名称。

**4.【轻微】无统一错误码枚举**
业务异常用 `ApiCode` 枚举管理，但状态码在部分 Controller 中仍直接返回数字字面量（`code=200`），增加了不一致风险。

### 可操作建议
1. **P1** 统一 `CREATE TABLE IF NOT EXISTS`，或启用 Flyway/Liquibase 管理迁移
2. **P1** 建立统一的依赖 BOM 管理
