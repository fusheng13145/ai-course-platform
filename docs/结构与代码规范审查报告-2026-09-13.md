## §1 结论摘要

### 1.1 总体判定

项目**工程基建成熟度高于其结构规范度**。构建门禁（JaCoCo 阻断 / SpotBugs 0-bug / ArchUnit 6 条 / Trivy + OSV-Scanner）与安全设计（五层纵深、双提交 CSRF、HttpOnly Cookie）已达到生产项目水准；但**目录组织与命名规范存在系统性欠账**，且在四处已形成事实上的「同一功能多份实现」。

一句话结论：**代码质量纪律是好的，结构与命名纪律是缺的；而覆盖率门禁的可信度低于手册所声称的水平。**

## §2 目录组织问题

### 2.1 仓库根目录

**结论：根目录本身是干净的**（仅 5 个文件 + 8 个目录），符合「根目录仅保留必要项」的既定约定。但存在两处不属于根目录职责的内容：

| 问题 | 实测 | 建议 |

| `logo.png` 1.27 MB 置于根目录 | 单文件占根目录体积 99% | 移入 `docs/assets/` 或 `frontend/public/`；根目录只留 README 引用 |
| `calibration/` 84.5 MB 混入仓库工作树 | 其中 `backend.log` 84.3 MB、`samples.jsonl` 59 KB、`run_calib.out`、`mock_llm.log` | 脚本与报告保留；**运行产物（`*.log`/`*.out`/`*.jsonl`）入 `.gitignore` 并清理** |

### 2.2 后端 `com.aicourse` 包组织

实测 22 个一级包 / 509 个主源文件。问题集中在三层：

**① `service/` 包内混入具体类（分层不纯）**

`service/` 顶层 60 个文件中，**55 个接口 + 5 个具体类**：

```
AiQuotaService.java          ← class（无接口）
BusinessMetricsService.java  ← class（无接口）
DimensionMetricsService.java ← class（无接口）
HealthMetricsService.java    ← class（无接口）
PromptGuard.java             ← class，且命名不带 Service 后缀
```

同一包内「接口 + 实现类」并存，导致 `service/impl/` 的划分规则失效——读者无法从包名判断某类型是契约还是实现。**且这 5 个类无接口**，与其余 55 个走「接口 + impl」双文件的写法形成双重不一致。

> 建议统一：要么这 5 个类迁入 `service/impl/` 并补接口（若确需多实现/需被 Mock），要么明确约定「无多实现需求的类不拆接口」，并在手册写明判定标准。**不允许两种写法在同一包随机共存。**

**② `service/component/` 是桶包，且命名后缀三套并存**

36 个文件中：32 个 `*Component` + 2 个 `*Support` + 1 个 `*Util`，另有 `SubmissionJsonSupport`：

| 后缀 | 文件 |
| --- | --- |
| `*Component`（32） | `AiCoreComponent` / `AuthSessionComponent` / `SysBackupComponent` … |
| `*Support`（3） | `StudentTaskSupport` / `TeacherCourseSupport` / `SubmissionJsonSupport` |
| `*Util`（1） | `SysFileUtil` |

`*Support` 与 `*Util` 是工具/支撑类，**不属于「业务组件」语义**，混入 `component/` 使该包失去内聚性。同时 36 个组件平铺在一个包内，前缀覆盖 `Ai*`(4)/`Auth*`(3)/`Sys*`(5)/`Student*`(5)/`Teacher*`(4)/`Exam*`(3)/`Learning*`(4)/`Submission*`(3) 等 12 个域，无任何子分组。

**③ 单文件包过多（5 个）**

`aspect/`(1)、`event/`(1)、以及 `integration/` 下 `kg/`(3)/`rag/`(3) 等属于细碎但合理的划分；但 `aspect/` 只有 `OperationLogAspect` 一个文件，`event/` 只有 `NodeStatusChangedEvent`（且**该文件至今未提交**）——两个包各为一个类开设，建议合并至 `common/` 或按职责归并。

### 2.3 前端 `src/` 组织

**结构主体是按角色分包，方向正确**（views/admin 82、views/teacher 94、views/student 43、views/auth 5、views/common 9、views/error 2），但存在**三重粒度冲突**：

| 问题 | 实测 | 说明 |
| --- | --- | --- |
| **同一角色内页面的归属粒度不一致** | `views/teacher/` 根下平铺 `Courses.vue`/`CourseDetail.vue`/`CreateCourse.vue`/`Dashboard.vue`/`Exams.vue`/`Grades.vue` 6 个页面；而 `CourseDiscussion.vue`/`CourseGrades.vue`/`CourseExams.vue`/`CourseTasks.vue` 等 12 个同类页面却收进 `views/teacher/cockpit/` | 为何 `Grades.vue` 在根、`CourseGrades.vue` 在 cockpit？无规则可循 |
| **`views/teacher/components/` 是无域名的杂桶** | 15 个文件混合 `Cd*`(5，课程详情)、`Exam*`(4，无前缀)、`Tc*`(2，教师课程卡)、`Tg*`(4，教师成绩) | 一个「components」同时承载 4 个不相关域 |
| **`components/` 与 `views/*/components/` 边界失守** | `src/components/course/` 13 个文件（`Cls*`/`Cpt*`/`Cct*`/`Cgt*`/`Cds*`）实为**教师/学生角色专属**的课程页签面板，却放在全局公共组件目录；而教师自己的 `views/teacher/components/Tg*` 承载同类成绩面板 | 同一功能的组件被拆到两个顶层位置（`CgtGradeTable` vs `TgGradeTable`） |

**知识图谱域的四套并行实现（详见 §4.1）跨了三个目录层级**：

```
src/components/knowledge/       Knt*  (5)   ← 全局 components
src/views/teacher/tools/components/  Kg* (4) + Km* (3)   ← 教师
src/views/student/study/components/  Skg* (2)            ← 学生
```

**其他结构缺口：**

- `src/views/__tests__/functional-completeness.test.js` 测试的是 `@/api/*` 模块导入，却放在 `views/__tests__/`——**测试位置不镜像被测源**。
- `src/types/index.d.ts` 单文件 285 行承载全仓类型；而 `api/` 有 42 个模块各自定义类型，未收敛。
- `src/monitoring/`（1 个 .ts + 1 个测试）、`src/config/`（1 个 .ts）为单文件目录，且 `main.ts` 里已存在 `nprogress` 加载条，`request.ts` 又手写了一套 DOM 进度条（详见 §5.2）。

## §3 命名规范问题

### 3.1 未文档化的缩写前缀体系（前端最主要命名问题）

实测前端存在 **35 个组件前缀族**（≥3 成员的），全部为 2–3 字母缩写：

| 前缀 | 成员数 | 语义（需从代码反推，无文档） |
| --- | --- | --- |
| `Ci` / `In` | 6 / 6 | 互动（两套并行实现） |
| `Dsc` | 6 | 讨论（跨角色重复） |
| `Ac` | 5 | AI 中心面板 |
| `Cd` / `Cdu` / `Cds` / `Cqb` | 5/4/3/3 | 课程详情 / 学生课程详情 / cockpit 讨论 / cockpit 题库 |
| `Em` / `Ep` / `Qb` / `Qm` / `Kb` / `Kg` / `Km` / `Knt` / `Skg` | 5/4/5/5/4/4/3/5/2 | 考试、题库、知识库、知识图谱（**7 个前缀描述 2 个概念**） |
| `Tg` / `Cgt` | 4 / 4 | 成绩（两套） |
| `Ss` / `Nm` / `Ol` / `Kb` | 5/2/3/4 | 系统设置 / 通知管理 / 操作日志 / 知识库 |

**核心问题有三**：

1. **前缀语义无单一事实来源**。手册 §19.2 的命名条款只有一句「组件命名 `PascalCase.vue`」。`Knt`/`Kg`/`Km` 都是「知识图谱」，`Ep`/`Qb` 都是「题库」，新人必须逐个读文件才能解码。
2. **同一目录内前缀使用不一致**——这是规则失效的直接证据：

   | 目录 | 有前缀 | 无前缀（同目录） |
   | --- | --- | --- |
   | `views/admin/teaching/components/` | `Em*`(5) `Pc*`(3) `Qm*`(5) `Rm*`(3) | `GradeTable` `GradeFilterBar` `GradeAnalyticsPanel` `GradeDetailDialog` |
   | `views/admin/governance/components/` | `Eg*`(4) `Tsv*`(4) | `AnalyticsCharts` `AnalyticsMetricCards` |
   | `views/admin/user/components/` | `Pm*`(2) `Um*`(5) | `ClassEditDialog` `ClassListPanel` `ClassOrgTree` `ClassMemberManagerDialog` |
   | `views/teacher/components/` | `Cd*`(5) `Tc*`(2) `Tg*`(4) | `ExamDetailDialog` `ExamFormDialog` `ExamListPanel` `QuestionPickerDialog` |

3. **前缀长度不统一**：多数为 2 字母（`Ad`/`Eg`/`Kb`/`Qm`），部分 3 字母（`Tsv`/`Cdu`/`Cgt`/`Cqb`/`Dsc`），还有个 `Class` 用全词。同一体系内 2/3/全词三种长度混用。

### 3.2 后端 `dto/` 命名三套并存

`dto/` 77 个文件的命名分布：

| 后缀 | 数量 | 评价 |
| --- | --- | --- |
| `*DTO` | 51 | ✅ 正确 |
| `*VO` | 16 | ❌ **位置错误**：应为出参对象，却在入参包 |
| `*Request` | 8 | ❌ **第三套命名**（`EssayRequest`/`QaAskRequest`/`RefreshTokenRequest`/`ResetPasswordRequest`/`SendCodeRequest`/`VerifyCodeRequest`/`QaContinueRequest`/`LearningPathRequest`）——与 `*DTO` 语义完全相同 |
| `*Result` | 1 | ❌ `ExamAnswerResult` 应为 `*VO` |
| 无后缀 | 1 | ❌ `ClientInfo`（值对象，且**未提交**） |

**且存在 3 组同名跨包类**：

| 类名 | 所在包 A | 所在包 B |
| --- | --- | --- |
| `CourseDetailVO` | `com.aicourse.dto` | `com.aicourse.vo` |
| `KnowledgeGraphVO` | `com.aicourse.dto` | `com.aicourse.vo` |
| `KnowledgePathPlanVO` | `com.aicourse.dto` | `com.aicourse.vo` |

同名类仅靠包名区分，一旦任一文件使用通配符导入即产生编译/语义歧义，是典型的「命名即歧义」缺陷。

此外，同一概念在两端各有一套并行类：`dto/KnowledgeGraphEdgeVO` + `dto/KnowledgeGraphNodeVO` ↔ `vo/GraphDataLinkVO` + `vo/GraphDataNodeVO`——**4 个类描述 2 个概念**。

### 3.3 测试类命名

实测 219 个测试文件的命名画像：

| 后缀模式 | 数量 | 占比 |
| --- | --- | --- |
| `*Test` | 169 | 77.2% |
| `*CoverageTest` | 26 | **11.9%** |
| `*BoostTest` | 20 | **9.1%** |
| `*IT` | 1 | 0.5% |
| 其他 | 3 | 1.4% |

`Coverage`/`Boost` 是**以度量指标而非被测行为命名的测试类**，占 21.0%。手册 §10 仅记录「含 26 个 `*CoverageTest`」，**遗漏了 20 个 `*BoostTest`**，导致统计口径不完整。

同时存在**同一命名目标两种写法**：

```
ExamSessionServiceTest.java          + ExamSessionServiceBoostTest.java       ← 接口名
ExamSessionServiceImplTest.java      + ExamSessionServiceImplBoostTest.java   ← 实现类名
```

即 `ExamSessionServiceImpl` 一个类有 **4 个测试类**。同类问题在 `AuthServiceImpl`（3 个）、`AIController`/`AuthController` 等 30 组中出现（详见 §4.2）。

### 4.3 微重复（前端 `request.ts`）

同一文件内定义了两个逻辑完全相同的请求键生成函数：

```ts
function getRequestKey(config) {                          // L113
  const { method, url, params, data } = config || {}
  return `${method}:${url}:${JSON.stringify(params)}:${JSON.stringify(data)}`
}
function generateReqKey(config) {                         // L141
```

差异仅在于分隔符与 `null` 处理方式，维护时需双改。属明显应合并的重复。

### 6.1 前端类型检查缺失（P0）

### 6.2 覆盖率门禁口径严重不对称

| 端 | 门禁指标 | 阈值 | 口径 |
| --- | --- | --- | --- |
| 后端 | JaCoCo LINE / BRANCH | **85% / 65%**（`haltOnFailure=true`） | 全量类（371 类） |
| 前端 | lines / functions / branches / statements | **7 / 20 / 60 / 7** | 仅 8 个逻辑层 `.ts` 目录，**排除全部 287 个 `.vue`** |

`vitest.config.ts` 的注释解释了排除 `.vue` 的合理性（「287 个 .vue 视图组件单元测试投入产出比低」）——**该判断本身成立**。但需正视由此产生的两个事实：

1. **前端覆盖率读数不可与后端并列呈现**。后端 94% 与前端 lines 7% 不是同一口径下的两个数字，并列会让读者误判前端质量。
2. **lines ≥7% 的阈值实质不构成门禁**。`vitest.config.ts` 注释自述「逻辑层实测基线 lines 8.3%」，阈值 7% 意味着**允许覆盖率倒退 1.3 个百分点才触发失败**——与手册 §46.3「只许上调、不得下调」的硬规则在字面上不冲突，但**缺乏实质约束力**。

### 6.3 覆盖率门禁可信度（P0，与 §4.2 同源）

如 §4.2 所述，46 个 `Coverage`/`Boost` 测试类（13,360 行，占测试代码 28.1%）的存在目的被代码注释承认为指标填充。这带来三个必须正视的后果：

| 后果 | 说明 |
| --- | --- |
| **读数不可用于质量推论** | LINE 94.06% 不能推出「代码受 94% 行为验证」；`dto` 包的 getter/setter 反射调用与业务逻辑覆盖在 JaCoCo 中权重相同 |
| **阈值「只许上调」的方向正确但基线失真** | 若要上调阈值，须先剔除填充量、得出真实基线，否则上调的是「填充能力」而非「测试能力」 |
| **30 组重复测试类增加维护成本且掩盖缺口** | 同一被测类 2–4 份测试，修改被测行为时需同步多点；同时 `DtoPackageCoverageTest`(344 行) 这类反射测试对真实缺陷的发现率为 0 |

### 9.2 分层

1. **Controller**：只做参数绑定、`@PreAuthorize`、调 Service、返回 `ApiResponse`；禁止业务分支。
2. **Service 接口**：只放 `interface`。实现一律在 `impl/`。无多实现需求者**不拆接口**（并写入判定标准，见 §8.2）。
3. **Service 组件**：按域分子包；只放有依赖注入需求的有状态协作者。
4. **Mapper**：只做数据访问，禁止业务规则。
5. **异常**：业务异常统一 `BusinessException`；**禁止 `new RuntimeException`**；集成层降级必须 `log.warn` 留痕。
6. **注入**：统一构造器注入（`@RequiredArgsConstructor`），**禁止字段注入 `@Autowired`**。
7. **日志**：统一 `@Slf4j`，**禁止全限定名 `LoggerFactory.getLogger(...)` 内联调用**；禁止 `System.out/err`/`printStackTrace`。
8. **前端**：所有请求经 `api/`；UI 与传输分离（HTTP 层不得操作 DOM）；日志统一走 `utils/logger`，禁止裸 `console.*`。
9. **前端类型**：`tsconfig` 开启 `strict`；**构建必须包含 `vue-tsc --noEmit`**。

### 9.3 测试

1. **一个被测类一个测试类**，命名 `<Target>Test`。同类多份测试必须合并。
2. **禁止以覆盖率指标命名测试**（`*CoverageTest`/`*BoostTest`）。覆盖率是测试的**副产物**，不是测试的**目的**。
3. 覆盖率统计**必须排除**以下内容，否则读数不可用于质量判定：
   - 纯数据载体（`dto/`、`vo/`、`entity/`、`enums/`）的 getter/setter/`equals`/`hashCode`/`toString`
   - 反射驱动的批量执行测试
4. **阈值上调前必须先剔除填充量得到真实基线**，否则「只许上调」上调的是填充能力而非测试能力。
5. 测试文件位置镜像被测源：`api/` 的测试在 `api/__tests__/`，不得置于 `views/__tests__/`。
6. 前端测试与源同扩展名（`.test.ts`）。

### 9.4 门禁与 CI

| 项 | 目标 |
| --- | --- |
| 前端类型检查 | **新增** `npm run typecheck`（`vue-tsc --noEmit`），纳入 `frontend-quality` 作业并阻断 |

## 11.2 关键项详录

### P0-1 前端类型检查：从「零检查」到「棘轮门禁」

**过程与取证（含一次失败与修正）**

初次诊断发现 715 条错误 / 116 文件，其中 **648 条为 `unknown` 类型上的属性访问**。根因是 §46.1-15「`any` → `unknown`」迁移的连带后果——`unwrap()` 的泛型默认值由 `any` 改为 `unknown` 后，全仓 `unwrap()` 调用的返回值全部不可访问属性。

先后做了 3 次对照实验（每次均以 `vue-tsc` 实测，不凭推断）：

| 实验 | 改动 | 错误数 | 判定 |
| --- | --- | --- | --- |
| 基线 | 原始状态 | **715** | — |
| 实验 1 | `request` 门面声明返回 `ApiPayload`（已解包数据） | 915 ❌ | 失败：拦截器实际返回**完整信封**而非已解包数据，此声明与运行时不符，且破坏了既有的 `r.data` 惯用法 |
| 实验 2 | `request` 门面声明返回 `ApiEnvelope<ApiPayload>` | 846 ❌ | 失败：修好了 `r.data`，但使 145 处手写双取值产生联合类型（`ApiPayload \| ApiEnvelope<ApiPayload>`） |
| **实验 3** | **仅改 `unwrap` 默认类型 `unknown` → `ApiPayload`，门面保持原样** | **598 ✅** | **采纳**：净减 117 条，且改动本身设计正确（`Record<string, unknown>` 描述后端返回体，保留字段访问能力又不同于 `any`） |

> 关键证据：拦截器成功分支 `return data`（`data = response.data`）返回的是**完整业务信封**，而非解包后的业务数据。此事实推翻了实验 1 的前提，也是实验 1/2 反而变差的原因。

**最终交付**

- `src/utils/response.ts`：新增 `ApiPayload` 类型（`Record<string, unknown>`），`unwrap<T = ApiPayload>`；类注释与实现对齐（原注释写「缺省为 any」而实现为 `unknown`，二者本就矛盾）。
