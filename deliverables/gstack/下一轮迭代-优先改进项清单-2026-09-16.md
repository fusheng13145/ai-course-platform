## 2. 每项问题的定位与说明

### P0-1 · #22 登录锁定 DoS（缺陷修复 / 安全）

- **具体问题**：`AuthSessionComponent.java:88-97` 在密码错误时 `failedAttempts = user.getFailedLoginAttempts() + 1`，达 `MAX_FAILED_ATTEMPTS=5`（`AuthSessionComponent.java:42`）即对该**账户**置 `lockedUntil = now + 15min`（`LOCK_MINUTES=15`，`:41`）。锁定对象是**受害者账户**，而非攻击者的来源 IP。`User.java:74` 的 `lockedUntil` 字段为账户级。
  → 任何知道目标用户名/邮箱的人，连发 5 次错误密码即可让该账户（含 admin）15 分钟内无法登录，且可循环实施。
- **影响范围**：全平台任意账号的**可用性**；可针对管理员做有目的 DoS；若 B1 注册验证码分支被弱化，可与免费账号叠加放大。这是本轮唯一真实可达的「阻断级」安全缺陷。
- **推荐处理方式（最小可行 + 正确）**：将失败计数与锁定的粒度从「账户」改为「**来源 IP**（或 IP+账户）」，使 DoS 目标是攻击者自身 IP 而非受害者账户。
  1. 新增 Redis 失败计数键 `login_fail_ip:<ip>`，达阈值锁定该 IP（非账户）；账户级锁定仅作同 IP 内的二次防御。
  2. 登录入口已传入 `clientInfo`（`AuthSessionComponent.java:84/89/100` 的 `saveLoginLog(..., clientInfo, ...)`），可直接提取来源 IP 复用，无需改签名。
  3. 阈值/时长改为 `@Value` 配置化（`MAX_FAILED_ATTEMPTS`/`LOCK_MINUTES` 现硬编码为常量）。
  4. 补充单测：① 攻击者 IP 连续失败→该 IP 被锁、受害者从其他 IP 仍可登录；② 同 IP 正确密码可重置计数。
  5. 可叠加 Sentinel 对 `/auth/login` 的 per-IP 流控作为纵深防御（现有 `SentinelWebFilter` 可承接）。
- **坐标**：`AuthSessionComponent.java:41-42`（常量）、`:88-101`（锁定逻辑）、`User.java:74`（`lockedUntil`）；建议新增 Redis 失败计数组件 + 配置项。

### P1-1 · B3 明文部署 302 + 令牌明文（缺陷修复 / 部署·凭据）

- **具体问题**：`docker-compose.yml:148` 现为 `REQUIRE_HTTPS: ${REQUIRE_HTTPS:-false}`——**默认已 false**（前轮报告记 `true`，已更正）。但 `frontend/nginx.conf` 仅 `listen 80`（`:12`）且无证书卷；`nginx.conf:1-10` 注释已声明风险：若运维将 `REQUIRE_HTTPS` 置 `true` 又不加 TLS 终止反代，后端会把 `/api/**` 302 到不存在的 443，全站 API 失效，且令牌经明文传输。
- **影响范围**：采用「方式二 Docker 部署」且误配 `REQUIRE_HTTPS=true` 的生产/评估环境（全站不可用 + 凭据泄露）。默认 `false` 已大幅收窄爆炸半径，但缺「误配即失败」的护栏。
- **推荐处理方式**：① 在 `SecurityConfig`/启动期加 **fail-fast 护栏**：若 `REQUIRE_HTTPS=true` 且请求无 `X-Forwarded-Proto: https`（无 TLS 终止信号）则启动告警或拒绝，避免明文栈静默 302；② 在 README「方式二」明确「置 true 前必须先加 TLS 终止反代」。最小改动=护栏+文档。
- **坐标**：`docker-compose.yml:148`；`frontend/nginx.conf:1-10,12`；`application*.yml` 的 `REQUIRE_HTTPS` 消费点；`README.md` 部署章节。

### P2-1 · DB 口令回退 footgun（逻辑补全 / 部署配置）

- **具体问题**：`.env.example:27-28` 注释 `SPRING_DATASOURCE_PASSWORD: ${MYSQL_APP_PASSWORD:-${MYSQL_ROOT_PASSWORD}}`——若运维只设 `MYSQL_ROOT_PASSWORD` 而漏设 `MYSQL_APP_PASSWORD`，应用以 `aicourse_app` 用户 + **root 口令**连接，鉴权失败致启动失败（非 root 直连，但是部署易踩的坑）。
- **影响范围**：部署配置正确性，影响首启可用性；不属于「以 root 直连」安全漏洞（用户名已是 `aicourse_app`）。
- **推荐处理方式**：将口令回退改为「缺失即 fail-fast 拒绝启动」或文档硬性要求必须设 `MYSQL_APP_PASSWORD`；并在 `docker-compose.yml` 显式注入 `SPRING_DATASOURCE_USERNAME=aicourse_app` 与 `SPRING_DATASOURCE_PASSWORD=${MYSQL_APP_PASSWORD}`（不回退 root）。
- **坐标**：`.env.example:27-28`；`docker-compose.yml:117` 附近 env 注入段。

### P2-2 · #14 前端 401 静默刷新（逻辑补全 / 前端）

- **具体问题**：后端 `GlobalExceptionHandler.java:72-78` 已对 `BadCredentialsException` 正确返回 **401**（语义无误）。但前端响应拦截器在收到 401 时是否「静默重试/刷新」导致死循环或体验异常，需浏览器实测确认。原报告标注「改动激活前端 401 静默刷新，需浏览器实测」。
- **影响范围**：登录失败 / 会话过期的前端体验，潜在重试风暴。
- **推荐处理方式**：浏览器实测「登录失败」与「令牌过期」两条路径；前端拦截器对 401 应清空本地会话并跳登录页，**禁止无界重试**。属「验证 + 小修」。
- **坐标**：前端 axios 拦截器（`src/api/request` 或 `src/utils/request`）；后端 `GlobalExceptionHandler.java:72-78`。

### P3-1 · `.trivyignore` 隐式豁免 4 条 CVE（配置治理 / 监控）

- **具体问题**：`.trivyignore` 仅列 3 条 Tomcat CVE（`65905`/`68525`/`65182`，`:6-8`），注释称 10.1.58 尚未发布到 Maven Central。但另有 4 条 CVE（`65183`/`65637`/`65927`/`68763`）版本区间命中 10.1.55，仅靠 Trivy 全局 `ignore-unfixed: true` **隐式**滤除；一旦 10.1.58 发布，这 4 条将涌现且豁免清单不匹配 → CI 意外转红、现象难排查。
- **影响范围**：CI 稳定性（非运行期安全缺陷）。
- **推荐处理方式**：建立「Tomcat 版本发布复核」待办——10.1.58 发布时升级 Tomcat 并据实更新 `.trivyignore`（补齐该 4 条或移除豁免）。当前无需改代码。
- **坐标**：`.trivyignore`；`backend/pom.xml` Tomcat 版本；CI trivy 配置。
