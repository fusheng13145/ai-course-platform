### 3.3 【#10b / P1-A】改密 / 重置密码后不吊销既有会话

```java
/**
 * 吊销指定用户的全部活跃会话（改密 / 重置密码后止损）。
 * 逐条复用 {@link #evictSessionCache(String)}，保证 Redis 缓存与 DB 状态一致。
 * @param userId 用户ID
 * @return 被吊销的会话数
 */
@Override
@Transactional(rollbackFor = Exception.class)
public int revokeAllActiveSessions(Long userId) {
    if (userId == null) {
        return 0;
    }
    List<UserSession> active = this.list(new LambdaQueryWrapper<UserSession>()
            .eq(UserSession::getUserId, userId)
            .eq(UserSession::getIsActive, true)
            .gt(UserSession::getExpiresAt, LocalDateTime.now()));
    if (active == null || active.isEmpty()) {
        return 0;
    }
    int n = 0;
    for (UserSession s : active) {
        if (s.getSessionToken() == null || s.getSessionToken().isBlank()) {
            continue;
        }
        evictSessionCache(s.getSessionToken());
        n++;
    }
    log.info("[session] 已吊销用户全部活跃会话: userId={}, count={}", userId, n);
    return n;
}
```

```java
private Rule resolveRule(String path, String clientIp) {
    if (path.startsWith("/api/auth/login")) {
        return new Rule("login", clientIp, loginLimit, loginWindowSeconds);
    } else if (path.startsWith("/api/auth/register")) {
        return new Rule("register", clientIp, registerLimit, registerWindowSeconds);
    } else if (path.startsWith("/api/ai/")) {
        return new Rule("ai", clientIp, aiLimit, aiWindowSeconds);
    } else if (path.startsWith("/api/common/verify-code")) {
        return new Rule("verify", clientIp, verifyLimit, verifyWindowSeconds);

    // 修复 #24：以下未认证端点同属「可对外发信 / 验证码爆破」面，此前完全不在任何规则内，

    else if (path.startsWith("/api/auth/send-code")
            || path.startsWith("/api/auth/verify-code")
            || path.startsWith("/api/auth/reset-password")
            || path.startsWith("/api/auth/reset-password-by-email")) {
        return new Rule("verify", clientIp, verifyLimit, verifyWindowSeconds);
    }
    return null;
}
```

### 3.10 【#28 / P1-A】备份失败却返回成功文件名（假备份）

**文件**：`backend/src/main/java/com/aicourse/service/component/sys/SysBackupComponent.java:137-184`

**当前代码**
```java

StringBuilder output = new StringBuilder();   // :150 全量堆内存
```

**目标行为**：mysqldump 不存在 / 非 0 退出 / 超时 → **抛异常**（调用方看到失败），绝不返回"看起来成功"的文件名。

**具体改法（三处，按优先级）**

1. **【必须】修假成功**（`:165-183`）：把 `return backupFileName` 的兜底路径改为抛异常：
```java
int exitCode = process.waitFor(10, java.util.concurrent.TimeUnit.MINUTES);  // 见第 2 点
if (!exitCode) {                       // 超时
    process.destroyForcibly();
    throw new BusinessException("数据库备份超时（10 分钟），已中止，未生成备份文件");
}
if (process.exitValue() != 0) {
    throw new BusinessException("mysqldump 执行失败，退出码=" + process.exitValue() + "，未生成备份文件");
}
// 落盘见第 3 点
```
并把 `:178-180` 的 `catch (Exception e) { log.warn(...); }` 改为：
```java
} catch (BusinessException e) {
    throw e;
} catch (Exception e) {
    // 修复 #28：此前这里 log.warn 后继续执行到 `return backupFileName`，
    // 调用方/运维会认为备份成功，从而在回滚时拿到一个不存在的恢复点 → 改为显式失败。
    throw new BusinessException("数据库备份失败：" + e.getMessage(), e);
}
```
2. **【必须】加超时**（`:159`）：`process.waitFor()` → `process.waitFor(10, TimeUnit.MINUTES)`，超时 `destroyForcibly()`（见上）。
3. **【建议】改直写磁盘 + stderr 分离**（`:145-162`）：
```java
pb.redirectErrorStream(false);                       // stderr 不再污染 .sql
pb.redirectOutput(backupFile);                       // 直接落盘，避免大库 OOM
Process process = pb.start();
// stderr 单独读，仅用于日志（可选：pb.redirectError(ProcessBuilder.Redirect.to(errFile))）
```
   > 注意：改为直写后，**失败时磁盘上会留下不完整的 `.sql`** —— 需在抛异常前 `Files.deleteIfExists(backupFile.toPath())`。

**关联点**
- 调用方（备份 Controller / `backup/mysql-backup.sh`）需能处理异常并返回明确失败。工程师需 grep `SysBackupComponent` 的调用点确认。
- 文档：`docs/项目手册.md` 备份章节需注明"备份失败会明确报错，不要只看返回的文件名"。
- 测试：新增 `backend/src/test/java/com/aicourse/service/component/sys/SysBackupComponentTest.java`，用 `ProcessBuilder` 不可用的场景（如把 `mysqldump` 换成不存在的命令，需可注入）断言抛 `BusinessException`。若命令路径硬编码不可注入，可先把命令名抽成 `@Value("${backup.mysqldump-path:mysqldump}")` 再测。

**风险与副作用**
- **行为变严**：此前"mysqldump 没装"时备份接口返回成功，现在返回失败。若某环境本来就没装 mysqldump，上线后备份功能会**开始报错**——这是**期望行为**（暴露真问题），但需提前告知运维。
- 超时值 10 分钟需按库大小调整；建议做成配置 `app.backup.timeout-minutes`。

**验证方式**
- 单测：注入不存在的 mysqldump 路径 → 断言抛 `BusinessException` 且 `Files.exists(backupFile) == false`。
- 实测：临时把 `mysqldump` 改名 → 触发备份 → 接口应返回明确错误（当前会返回"成功"）。
