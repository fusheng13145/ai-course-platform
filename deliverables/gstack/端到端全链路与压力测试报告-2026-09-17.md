### 3.3 安全维度（7 用例）


| 用例 | 断言 | 实测 |
| --- | --- | --- |

| S6a | **尝试层**：同账号连续失败达 5 次锁定 15 分钟 | 序列 `[400×4, 429]`，文案「登录尝试过于频繁，请15分钟后再试」✅ |
| S6b | **速率层**：IP 滑动窗口 10 次/60 秒 | 序列 `[200×10, 429×3]`，文案「请求过于频繁，请稍后再试。」✅ |

> **登录保护为两层结构（本轮首次分层验证）**：
> ① 速率层 `RateLimitFilter`：IP 滑动窗口 `ratelimit.login.limit=10 / window=60s`；
> ② 尝试层 `AuthSessionComponent`：同账号失败累计 `MAX_FAILED_ATTEMPTS=5` 即锁 `LOCK_MINUTES=15` 分钟。
> 尝试层阈值更低，故**失败路径下先触发**。原脚本单层断言（期待第 11 次才 429）因此失效，已重构为 S6a/S6b 分层断言。详见 §5.2。

## 4. 压力测试结果

### 4.1 测试设计

- **工具**：`deliverables/gstack/e2e_stress_verify.py`（仅标准库 `threading` + `http.client`，无外部依赖，任意机器可复跑）。
- **连接复用**：每工作线程持有独立 keep-alive 连接，避免握手开销污染延迟读数。
- **角色路由**：读清单逐条声明所需角色（学生/教师），按角色分发 Cookie —— 避免教师专属端点被学生身份访问而把「脚本错配」计入失败率。
- **读写分离计价**：读路径（不受 IP 限流管辖）与写路径分别统计。
- **业务拒绝与故障分离**：声明为可预期的非 2xx（如并发唯一约束 409）计入「业务拒绝」，其余非 2xx 计入「异常」。
- **事后健康校验**：压测结束后重新登录并打三个业务读接口，证明「高负载后系统仍可用」。

## 5. 发现的问题与处置

> **分级口径**：🔴 阻塞 ｜ 🟠 高 ｜ 🟡 中 ｜ ⚪ 低 / 观察项。本轮**无 🔴🟠🟡 项**。

### 5.1 ⚪【脚本滞后，已修复】深度验证 E 段断言未跟进 N-03 下线

| 项 | 内容 |
| --- | --- |
| 现象 | E2/E3/E5 报 FAIL：分片上传返回 501，期望 200；E5 期望 404/403 得到 501 |
| 根因 | 分片上传的「写字节」与「合并字节」逻辑从未实现，上线前全检结论 **N-03** 已将其**下线**：后端保留端点但恒抛 `BusinessException(501)`（`FileUploadSessionController.java:81,93`），前端 `uploadChunk`/`mergeChunks` 已从 `fileUpload.ts` 移除，并由 `functional-completeness.test.ts:52-53` 断言其不存在 |
| 判定 | **非产品缺陷**，属验证脚本未同步既定收缩决策 |
| 处置 | 修订 `e2e_deep_verify.py` E 段：断言改为「下线态契约」——恒 501 语义化拒绝、绝不 500、进度不推进；维度标题与文档字符串同步更新。修订后 **49/49** |

### 5.2 ⚪【脚本滞后，已修复】安全 S6 断言未跟进 P0-1 新增限流层

| 项 | 内容 |
| --- | --- |
| 现象 | S6 报 FAIL：期待第 11 次登录才 429，实测第 5 次即 429 |
| 根因 | 登录保护自 **P0-1「登录锁定 DoS」**修复后为**两层**：速率层（IP 滑动窗口 10/60 s，`RateLimitFilter`）+ 尝试层（同账号失败 5 次锁 15 分钟，`AuthSessionComponent.java:44-45,137,405-406`）。尝试层阈值更低，失败路径下先触发 |
| 判定 | **非产品缺陷** —— 产品实际比脚本预期**更严格**（安全性增强），旧断言把「更严格」误读为「不符合预期」 |
| 处置 | 重构 S6 为 **S6a（尝试层）/ S6b（速率层）** 分层断言，并在实测中分别取证两层的独立阈值。修订后 **7/7** |

**实证记录（两层各自独立取证）**：

```text
[S6a] FLUSHDB 后连续错误口令 → [400, 400, 400, 400, 429]
      第 5 次文案：「登录尝试过于频繁，请15分钟后再试」   ← 尝试层
[S6b] FLUSHDB 后连续成功登录 → [200 ×10, 429, 429, 429]
      第 11 次文案：「请求过于频繁，请稍后再试。」        ← 速率层（= 配置 10 次/60 秒）
```

### 5.3 ⚪【观察项】并发首次完成任务点返回 409，与顺序调用的幂等语义不一致

| 项 | 内容 |
| --- | --- |
| 现象 | 8 路并发对同一「任务点 + 学生」首次调用 `complete` → 状态码 `{200: 1, 409: 7}` |
| 数据结果 | `task_completions` 落库**恰好 1 条** —— 唯一约束 `uk_task_completion (student_id, task_id)` 生效 |
| 409 文案 | 「数据已存在（唯一约束冲突），请检查编号/名称等唯一字段」（`GlobalExceptionHandler:214-222`） |
| 判定 | **数据安全，且符合项目既有并发一致性契约** —— 深度验证 D1「并发重复写入仅保留 1 条、返回码含拒绝」判 PASS。故**不计缺陷** |
| 遗留改进建议 | ① 顺序调用恒 200（幂等）而并发首次返回 409，客户端双击/快速重试会看到报错；可捕获 `DuplicateKeyException` 后按幂等成功返回。② 409 文案面向上层「编号/名称唯一」场景，对「任务点重复完成」有误导，建议业务侧细分文案。 |
| 优先级 | ⚪ 低（不阻塞交付） |

### 5.4 ⚪【观察项】分片上传端点呈「半退役」状态

| 项 | 内容 |
| --- | --- |
| 现象 | `POST /upload-sessions`（建会话）仍开放且返回 200，但 `/chunks/{i}` 与 `/merge` 恒 501 |
| 影响 | 客户端可创建**永远无法完成**的上传会话，属死面；前端已不再调用，无实际影响 |
| 建议 | 若确认不再恢复分片上传，建议一并下线建会话端点（或在文档中显式标注为保留的兼容端点） |
| 优先级 | ⚪ 低 |

| 项 | 内容 |

```bash
# 0) 前置：MySQL(3306) 与 Redis(6379) 已运行；仓库根有 .env；backend/target/*.jar 已是最新
#    （改了后端代码务必先重新打包，否则跑的是旧产物）

# 1) 以「功能姿态」常驻启动后端（CSRF 关、登录限流 200）
#    必须以宿主后台任务方式运行，前台会阻塞且进程可能被回收
python scripts/run-backend-for-e2e.py functional

# 2) 核心功能三件套
cd deliverables/gstack
python e2e_verify_network_course.py    # 主链路 75
python e2e_deep_verify.py              # 多维深度 49
python e2e_stress_verify.py            # 压力测试（可加 --quick 走快速档）

# 3) 切换「安全姿态」（CSRF 默认开、登录限流默认阈值）
#    先停掉功能姿态后端，再：
python scripts/run-backend-for-e2e.py secure
cd deliverables/gstack && python e2e_security_verify.py   # 安全维度 7
```

**注意**：功能轮与安全轮**姿态不可混用**；两轮起测前脚本均会自行 `FLUSHDB`，无需手工清 Redis。
